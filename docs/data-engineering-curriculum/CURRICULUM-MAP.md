## How to author from this map

1. One level per file: `lib/tutorials/sql/curriculum/level{N}.ts`, exporting `sqlLevel{N}`, pushed
   into `SQL_LEVELS` in `curriculum/index.ts`. Follow `level6.ts` for structure and voice.
2. Lesson ids are `de-l{N}-{slug}` exactly as written here. Exercise ids are `{lessonId}-apply` and
   `{lessonId}-practice`. These ids key stored progress, so they are frozen once shipped.
3. Seeds are module-scoped constants named after the real artifact they simulate.
4. **Never hand-type an `expected` set.** Generate it by running the reference SELECT through the
   shipped sql.js WASM (the scratchpad `sqlgen/gen.mjs` harness), the same way L6 did.
5. House convention, verified across L1-L6: `referenceSolution` ships on **apply** and on **drills**,
   never on **practice**. Verify practice expected sets with a side reference file that is not
   committed.
6. Every workspace exercise whose script legitimately grows an append-only table on rerun MUST set
   `idempotencyTables: [...]` naming only the tables required to be stable. A bare
   `checkIdempotency` compares whole-workspace state and would fail every correct solution.
7. SQLite dialect only: no `MERGE` statement (teach merge semantics via
   `INSERT ... ON CONFLICT DO UPDATE` or delete+insert, and show real `MERGE INTO` in prose), no
   `CEIL`, no network.
8. Content rules: prompts lead with the deliverable, no em dashes in learner-facing prose, drills
   open with `**Easy.**` / `**Medium.**` / `**Hard.**`, teach closes with "On a real platform this
   differs" and an "Interview nuance" callout where transferable.

## Deferred, deliberately

Free-response design exercises are **not** available to this course in v1: `SqlLessonPlayer` is
typed to `SqlLesson`, and the design-answers API allowlists only `sd-` prefixed ids
(`lib/tutorials/design-answers.ts`). Where a lesson wants an open design answer (the "design a daily
ingestion pipeline" rehearsal in L8, the Spark slow-job capstone in L10), the map uses a graded SQL
exercise plus a written model answer in teach markdown, and records the free-response variant as
deferred. Wiring `DesignExercise` into this course is a real follow-up, not an oversight.

## What the reviewer changed

A coverage critic reviewed all five drafts against the shipped SQL curriculum, `RESEARCH.md`, and
the grading engine, and raised 19 issues; each level was then revised. The substantive corrections,
recorded so they are not re-litigated:

- **Duplication with shipped SQL levels was the dominant failure.** L5 already ships high-water-mark
  incremental extraction with a control table, write-audit-publish quality gates, and CDC changelog
  application. Those L8 lessons were rescoped from "teach it" to "audit what it silently loses",
  and the drafts' false novelty claims were corrected.
- **`idempotencyTables` was missing.** Several pipeline exercises were ungradable as drafted.
- **Two levels claimed the same lesson** (`de-l7-upsert-merge-semantics` and its L8 twin); L8 keeps
  the canonical idempotency arc, L7 keeps only what the table format adds.
- **Spark coverage was one lesson short** of the research's 7-9 mandate; a narrow-vs-wide and
  broadcast-threshold lesson was added, scoped as a deepening of L6 rather than a repeat.

## Level 7 - Warehouses, Lakehouse & Dimensional Modeling (slug: warehouses-lakehouse, section: Cloud & Data Platforms)

**Tagline:** Go inside the systems the lake feeds: how an MPP warehouse places and prices your data, how to turn the dimensional modeling SQL Levels 3-5 already taught into interview-ready answers, and how Iceberg turns files into transactional tables. **Estimated hours:** 7. **Research grounding:**
- Finding 3 / §2.4 / §6.5: data modeling is the most-interviewed junior skill, and the platform already teaches the Kimball canon: SQL Module 3.5 (Dimensional Modeling Introduction, incl. 'Facts, Dimensions, and Grain') and SQL Module 4.3b (Dimensional Modeling in Depth: star vs snowflake, fact types, dimension patterns, SCD Type 2 and its loader capstone), plus SQL Level 5's point-in-time SCD2 joins. Module 7.2 therefore does not reteach; it compresses that canon into interview rehearsal on the verbatim "ride-share driver moves cities" scenario, grades only what is new, and adds the one modeling decision no earlier level teaches: Kimball vs One Big Table with the ~10 GB join-side heuristic (implication 3, §2.4).
- §3.5 / §6.5: Redshift appears in 76% of AWS-flavored loops and sort/dist-key reasoning (incl. spotting DS_DIST_BOTH plans) is "the archetypal question"; module 7.1 grades exactly that over simulated table-stats and query-plan tables.
- §2.2 / implication 19: Iceberg is the de facto open-lakehouse standard and juniors must know "the problem, not the spec"; the research prescribes simulating its catalog (snapshots, manifests, files) for time-travel and pruning questions in SQL, with MERGE taught via `INSERT ... ON CONFLICT` (§5.3 sql.js note).
- Finding 12 / §3.9 / implication 45: Azure is ~34% of US DE postings, concentrated in the enterprise verticals that dominate Midwest/Michigan hiring. Module 7.4 delivers the cross-cloud translation layer and the DP-700-era framing (never DP-203) only; it is explicitly not the Azure module. The Tier 1 mandate of a dedicated ~6-10 lesson Azure/ADF module (implications 9, 25, 33) is scheduled in Level 8 beside the orchestration and incremental-load content, where the ADF watermark dual-label already lives (delivery note in the module 7.4 intro).
- Finding 9 / §7 / implication 12: scaffolding fades inside every module, ending in unscaffolded goal-state exercises (the direct counter to DataCamp's #1 complaint).

**Lesson count note:** 13 lessons, one over target. Research finding 3 justifies the flex, but the flex now belongs to module 7.2's fourth slot: with SQL Levels 3-5 owning first teaching of the Kimball canon, three lessons compress grain, additivity, and SCD2 into review-plus-rehearsal arcs, and the fourth carries Kimball vs One Big Table, the genuinely missing modeling lesson.

### Module 7.1 - Inside the Cloud Warehouse (id: de-l7-warehouse-internals)
The MPP warehouse from the inside: nodes and slices, distribution and sort keys read off simulated table stats and query plans, and the loading and billing models that decide what a query costs. Deepens L6's file-engine shuffle lessons (sql-l6-distributed-execution, sql-l6-skew-and-joins) into the warehouse, where distribution is chosen up front instead of paid per query. Grounded in §3.5 (Redshift 76% of loops) and §3.1/§3.4 (cost-model phrasing on DEA-C01).

#### de-l7-mpp-architecture - Inside an MPP Warehouse: Nodes, Slices, and the Slowest Slice [medium] [~26 min]
- **Summary:** Explain how an MPP warehouse spreads a table across compute nodes and slices, and find data skew in slice-level row counts.
- **Skills:** MPP architecture, leader vs compute nodes, slices, columnar storage in a warehouse, data skew, GROUP BY, MIN/MAX.
- **Teach:** Leader node plans, compute nodes execute, each node owns slices and every distributed table is sharded across all of them; a query runs on every slice in parallel and finishes at the speed of the slowest one. Contrast with L6: the file engine assigned splits at read time, the warehouse placed rows at load time, which is why placement is a design decision here. csdiagram: tree of leader node -> 2 compute nodes -> 4 slices with row counts per slice. Live demo: slice-level row counts for one skewed table. "On a real platform": Redshift exposes this via STV_SLICES and SVV_TABLE_INFO; Snowflake hides placement behind micro-partitions. Interview nuance: "an MPP query finishes at the slowest slice" is the one-sentence answer that shows systems understanding.
- **Seeds:** `warehouse_slices(node_id, slice_id, table_name, rows_on_slice, mb_on_slice)` simulating Redshift's slice-level system views; `warehouse_tables(table_name, diststyle, tbl_rows)`.
- **Apply:** "Write a query that returns each table's slice spread as `(table_name, min_rows, max_rows)`, widest spread first, over `warehouse_slices`." Single-file, orderMatters + assertColumnNames. Proves the learner can read physical placement per table.
- **Practice:** "Write a query that returns the tables where the busiest slice holds more than twice the rows of the quietest, as `(table_name, skew_ratio)` rounded to 2 decimals." Single-file, guided hints (module opener).
- **Extra practice:** total rows per node (easy); slice count per node (easy); percent of a table's rows on its hottest slice (hard).
- **Interview rationale:** Redshift is in 76% of AWS loops (§6.5); "why is one node pegged at 100% while the rest idle" is the entry skew question this arms.

#### de-l7-dist-sort-keys - Distribution Styles, Sort Keys, and Reading the Query Plan [hard] [~30 min]
- **Summary:** Choose KEY/ALL/EVEN distribution and a sort key from table stats, and spot DS_DIST_BOTH redistribution in a simulated query plan.
- **Skills:** DISTSTYLE KEY/ALL/EVEN, sort keys, zone maps, skew_rows, query-plan reading, joins, CASE classification.
- **Teach:** Distribution decides where rows live before any query runs: KEY co-locates joins, ALL copies small dimensions to every node, EVEN round-robins facts nobody joins on. The plan tells you when you chose wrong: DS_DIST_NONE is co-located, DS_BCAST_INNER broadcasts, DS_DIST_BOTH reshuffles both sides and is the red flag interviewers name (§3.5). Sort keys are the warehouse's zone maps, the same min/max skipping the learner met in sql-l6-row-groups-pushdown, now inside the warehouse. csdiagram: side-by-side co-located vs both-redistributed join. Live demo: the same join's plan steps under two diststyles. Interview nuance: "join on the dist key or broadcast the small table" is the expected sentence.
- **Seeds:** `warehouse_table_stats(table_name, diststyle, dist_key, sortkey1, tbl_rows, skew_rows, size_mb)` mirroring Redshift SVV_TABLE_INFO; `query_plan_steps(query_id, step_no, operation, dist_type, rows_out, mb_moved)` mirroring EXPLAIN output.
- **Apply:** "Write a query that returns every query whose plan contains a DS_DIST_BOTH step, as `(query_id, mb_moved)`, most data moved first." Single-file. Proves the learner can find the expensive redistribution by reading plan metadata.
- **Practice:** "Write a query that recommends a distribution style for each table as `(table_name, recommended_diststyle)`: 'ALL' when tbl_rows < 500000, 'KEY' when dist_key is not empty, else 'EVEN'." Single-file CASE over `warehouse_table_stats`, lighter scaffold.
- **Extra practice:** tables where skew_rows > 4 * tbl_rows/slice-count baseline (medium); join steps pairing tables with different dist keys (hard); largest unsorted table (easy).
- **Interview rationale:** Sort/dist-key selection with DS_DIST_BOTH plan reading is cited verbatim as the Redshift interview archetype (§3.5, §6.5).

#### de-l7-loading-and-cost - COPY from Stage, Never Row Inserts, and the Two Billing Models [medium] [~28 min]
- **Summary:** Explain why warehouses load via parallel COPY from object storage, and price the same workload under per-TB-scanned vs per-second-compute billing.
- **Skills:** COPY from stage, bulk vs row loading, commit overhead, per-TB-scanned pricing, per-second compute pricing, aggregation, SQL cost arithmetic.
- **Teach:** Warehouses ingest by pointing COPY at a stage of files in object storage and loading them in parallel across slices (one file per slice as the heuristic); row-by-row INSERT pays a commit and a columnar rewrite per statement and is the classic anti-pattern. Then the money: Athena/BigQuery-style engines bill $5 to $6.25 per TB scanned, Snowflake/Redshift-style bill compute seconds; the same dashboard is cheap on one and ruinous on the other depending on query shape. Live demo: rows-per-second by load method from the load log. "On a real platform": Snowflake COPY_HISTORY and Redshift STL_LOAD_COMMITS are the real logs behind the seed. Interview nuance: "why is inserting 10,000 rows one at a time slow in a warehouse" is a favorite trap; commit-per-statement is the answer.
- **Seeds:** `load_history(load_id, target_table, load_method, files_loaded, rows_loaded, mb_loaded, duration_s)` with 'copy_from_stage' vs 'single_row_insert' rows showing a ~100x throughput gap; `query_billing(query_id, tb_scanned, compute_seconds)`.
- **Apply:** "Write a query that returns each load method's throughput as `(load_method, rows_per_second)`, fastest first." Single-file. The expected set proves the COPY gap with real numbers.
- **Practice:** Module boss, no starter scaffold: "Write a query that returns each query's cost under both billing models as `(query_id, scan_cost_usd, compute_cost_usd, cheaper_model)`, using $5.00 per TB scanned and $0.0004 per compute second, rounded to 4 decimals." Single-file.
- **Extra practice:** apply the 10 MB minimum-scan rule and find queries where it dominates (medium); total monthly bill per model, rounded to 2 decimals (easy).
- **Interview rationale:** DEA-C01 Domain 2 loading patterns plus the "cheapest option" cost instinct (§3.1, §3.4); Capital One and Amazon loops both probe warehouse loading tradeoffs.

### Module 7.2 - Dimensional Modeling: Rehearsal and the Missing Debate (id: de-l7-dimensional-modeling)
The platform already teaches the Kimball canon: SQL Module 3.5 (Dimensional Modeling Introduction) covers facts, dimensions, and declared grain; SQL Module 4.3b (Dimensional Modeling in Depth) covers star vs snowflake, the star-schema load with surrogate keys, fact types and measure additivity, and SCD Type 2 through its loader capstone; SQL Level 5 grades the point-in-time (as-of) join against an SCD2 dimension. This module is explicitly review-plus-extension, and says so on lesson one: it re-runs that canon as interview rehearsal on the verbatim ride-share scenario (finding 3), grades only what is new (an executable grain audit, the wrong-vs-right semi-additive side-by-side, a timed SCD2 change-batch applier), and spends its fourth slot on the one modeling decision no earlier level teaches: Kimball vs One Big Table with the ~10 GB join-side heuristic (implication 3, §2.4). Grading policy for the module: every money-bearing output column states an explicit ROUND(..., 2) so results never depend on floating-point summation order.

#### de-l7-grain-audit - Grain Rehearsal: Say the Sentence, Then Prove It in SQL [medium] [~22 min]
- **Summary:** Review declared grain from SQL Levels 3-4 in one screen, then do the new work: audit a raw extract against its declared grain with executable SQL.
- **Skills:** grain declaration (review), grain-violation auditing, GROUP BY/HAVING, ROW_NUMBER dedup, interview rehearsal habits.
- **Teach:** One-screen review, with pointers instead of reteaching: sql-l3's 'Facts, Dimensions, and Grain' already taught declared grain, narrow facts, and wide dimensions, and named "state the grain first, out loud" as the strong-candidate signal. What this lesson adds is the follow-up interviewers use to separate rehearsed candidates: after you say "one row per completed trip", prove the data respects it. The grain audit is that proof as a query, run before any star is built. The scenario is the verbatim ride-share extract the research cites. csdiagram: staging extract -> grain audit -> clean fact flow. Live demo: rows-per-trip check on the staging extract. Interview nuance: the audit query is a 60-second move in a take-home that reviewers explicitly notice; it converts the grain sentence from claim to evidence.
- **Seeds:** `staging_trips(trip_id, rider_id, driver_id, driver_name, driver_city, city, requested_at, completed_at, fare_usd, tip_usd)` simulating a raw ride-share extract with 3 duplicated trip rows planted.
- **Apply:** "Write a query that returns every trip violating the declared grain of one row per completed trip, as `(trip_id, row_count)`, worst first, over `staging_trips`." Single-file. Proves the grain-check habit as executable SQL; this audit is the new graded skill, not the grain concept.
- **Practice:** "Write a query that returns the true total fare revenue as `(clean_revenue)` rounded to 2 decimals, keeping one row per trip_id (latest completed_at wins) before summing." Single-file; fuses grain repair with the windowed-dedup canon (§6.3).
- **Extra practice:** distinct grain keys vs raw row count in one row (easy); revenue inflation percent caused by the duplicates, rounded to 1 decimal (medium).
- **Interview rationale:** "State the grain before drawing tables" is a named hiring signal (§6.2, §6.5); the audit is the follow-up probe, and it is the only part L3 did not already grade.

#### de-l7-semi-additive-audit - Semi-Additive Rehearsal: The Wrong Sum and the Right Sum, Side by Side [medium] [~24 min]
- **Summary:** Review measure additivity from SQL Level 4 in one screen, then grade the new artifact: one query showing the naive cross-day SUM next to the correct as-of total.
- **Skills:** additive vs semi-additive vs non-additive (review), periodic snapshots, ROW_NUMBER as-of aggregation, side-by-side proof queries.
- **Teach:** Pointer, not reteach: sql-l4's 'Fact Table Types and Measure Additivity' owns first teaching of transaction vs snapshot facts and the additivity ladder. The one-screen review restates it (event measures sum freely; snapshot balances sum across accounts on one day, never across days; ratios never sum, recompute from parts). What is new is the interview move: do not just name the trap, demonstrate it, producing the wrong number and the right number in the same result set so the interviewer sees the delta. Staged inside the same ride-share warehouse: a daily driver-wallet balance snapshot. Live demo: the naive cross-day SUM vs the as-of SUM on the seed, wrong answer shown on purpose. "On a real platform": bank and wallet warehouses run exactly this daily-balance snapshot; warehouse dialects add LAST_VALUE conveniences but ROW_NUMBER is portable. Interview nuance: "which measures on your fact are semi-additive" is the intern probe that follows any star answer (§6.5); the side-by-side is the rehearsed version of the answer.
- **Seeds:** `fact_wallet_snapshot(driver_id, as_of_date, balance_usd)` covering 6 drivers across 2 month-ends; `fact_payouts(payout_id, driver_id, paid_at, amount_usd)`; `dim_driver(driver_id, home_city)`.
- **Apply:** "Write a query that returns, per home_city for 2026-06, both the wrong naive sum and the correct month-end total as `(home_city, naive_total, correct_total)`, each rounded to 2 decimals: naive sums every snapshot row in the month, correct takes the latest snapshot per driver first." Single-file. The side-by-side is the new graded skill; making the wrongness visible is the point.
- **Practice:** "Write a query that returns the correct month-end balance per city for both month-ends as `(home_city, month_end, correct_total)` rounded to 2 decimals, latest row per driver within each month first." Single-file, reduced scaffold; extends the as-of pattern across a second time grain.
- **Extra practice:** recompute average payout correctly from SUM/COUNT instead of averaging per-day averages, rounded to 2 decimals (medium); which driver's balance moved most between month-ends (hard).
- **Interview rationale:** Additive vs semi-additive is on the verbatim intern probe progression (§6.5, §8 modeling row); L4 graded knowing the rule, this grades performing it under interview framing.

#### de-l7-scd2-rehearsal - SCD2 Under the Clock: Apply the Change Batch [hard] [~30 min]
- **Summary:** A timed interview rehearsal: apply an incoming multi-driver change batch to a Type 2 dimension with a rerunnable script, the step SQL Level 4's loader capstone set up and real loops run against the clock.
- **Skills:** SCD Type 2 (review), change-batch application, change-detection guards, close-and-insert scripts, idempotent scripts, as-of joins (review), timed rehearsal.
- **Teach:** Explicit about lineage: sql-l4's 'SCD Type 2' and 'Capstone: A Type-2 SCD Loader' built the mechanism, and sql-l5's 'Point-in-Time (As-Of) Joins Against an SCD2 Dimension' graded the join predicate; neither is retaught here. This lesson stages the verbatim interview instead: a driver moves cities, and you have roughly 25 minutes to apply the change batch correctly while narrating. One review screen: the version-row shape and the as-of predicate (fact date >= valid_from AND fact date < valid_to). csdiagram: timeline of driver 42's two version rows with a trip landing in each window. Live demo (review, ungraded because L5 graded it): the as-of revenue join splitting driver 42's revenue across both cities. Speaking notes taught alongside the script: "Type 2, and here is the join predicate" answers the question completely; most candidates stop at the type number. Forward pointer: CDC streams feed this change batch, which Level 9 builds.
- **Seeds:** `dim_driver_scd(driver_key, driver_id, driver_name, home_city, valid_from, valid_to, is_current)` with driver 42 moving 'Detroit' to 'Ann Arbor' on 2026-03-01; `fact_trips` with trips straddling the move; `driver_updates(driver_id, new_city, effective_date)` as the incoming change batch, including one no-op row (same city) to force a change-detection guard.
- **Apply:** Timed rehearsal (the prompt states the 25-minute target): "Write a script that applies `driver_updates` to `dim_driver_scd` as Type 2 changes: close each affected current row at the effective date and insert the new version, leaving unchanged drivers and no-op updates untouched." Workspace; hidden assertions verify window continuity and exactly one is_current row per driver; checkIdempotency on (a second run must change nothing). This applier, under the clock, is the new graded skill.
- **Practice:** Module boss, no starter scaffold, timed: "Write a script that applies a second batch in which one driver changes cities twice with two effective dates: versions must chain in order with continuous windows and a single is_current row." Workspace + checkIdempotency.
- **Extra practice:** find any overlapping validity windows as a quality check (hard); review drill referencing sql-l5: revenue by home_city as `(home_city, revenue)` rounded to 2 decimals, attributing each trip to the city current at completion (easy, labeled review).
- **Interview rationale:** Type 2 dominates SCD questions and "ride-share driver moves cities" is the literal example in the interview corpus (§6.5, finding 3); what candidates fail is not the concept L4 taught but executing the applier cleanly under time, which is exactly what this grades.

#### de-l7-kimball-vs-obt - Kimball vs One Big Table: The 10 GB Join-Side Heuristic [medium] [~26 min]
- **Summary:** Decide star schema vs One Big Table per data mart using consumer needs and the ~10 GB join-side heuristic, graded over simulated warehouse metadata.
- **Skills:** One Big Table pattern, denormalization tradeoffs, join-side sizing, conformed-dimension reuse, storage cost arithmetic, CASE classification, decision frameworks.
- **Teach:** The debate the Kimball canon skips and no earlier level teaches (implication 3, §2.4): modern columnar engines make one wide pre-joined table viable, and BI teams love it because every query is a single-table scan. Kimball still wins when dimensions are reused across facts, history must version (the SCD2 machinery from lesson 3 has nowhere to live in an OBT), or dimension updates would rewrite billions of fact rows. The working heuristic from the research: while the join side stays under roughly 10 GB the engine broadcasts it and star joins stay cheap, so keep the star; past that, join cost starts to dominate and pre-joining into an OBT (or dist-key co-location, lesson de-l7-dist-sort-keys' tool) earns its storage bill. Tie back to module 7.1 explicitly: this is the same broadcast-vs-redistribute physics, applied at design time instead of read from a plan. Live demo: the mart metadata with join-side sizes. Interview nuance: "would you just make one big table" is a real follow-up to any star answer; the strong response names the heuristic number and one cost of each path instead of picking a side dogmatically.
- **Seeds:** `mart_profiles(mart, fact_rows, fact_row_bytes, denorm_extra_bytes, fact_gb, total_dim_gb, dims_reused_elsewhere, dim_change_rate_pct, bi_only)` with 8 marts (the ride-share star among them) spanning both sides of the 10 GB line.
- **Apply:** "Write a query that classifies each mart as `(mart, recommendation)` using the given rules: 'obt' when total_dim_gb > 10 and bi_only = 1 and dims_reused_elsewhere = 0, 'star' when dims_reused_elsewhere = 1 or dim_change_rate_pct > 5, else 'either'." Single-file CASE, rules stated in the prompt.
- **Practice:** "Write a query that prices the denormalization as `(mart, star_gb, obt_gb, growth_factor)`: obt_gb is fact_rows times (fact_row_bytes + denorm_extra_bytes) converted to GB, both GB columns and the factor rounded to 1 decimal, biggest growth first." Single-file, reduced scaffold.
- **Extra practice:** marts whose recommendation flips if the heuristic threshold moves to 5 GB (medium); which mart pays the largest rewrite when one dimension attribute changes, in rewritten GB rounded to 1 decimal (hard).
- **Interview rationale:** §2.4 names Kimball-vs-OBT as a live debate junior candidates are expected to have an opinion on; the ~10 GB join-side number is what makes the answer sound experienced, and no other level in the course teaches it.

### Module 7.3 - The Lakehouse and Open Table Formats (id: de-l7-lakehouse-iceberg)
What Iceberg adds on top of the files-plus-catalog world L6 built: transactions, upserts, time travel, and self-healing file layouts, all taught by querying a simulated Iceberg catalog named after its real metadata tables (§2.2, implication 19). MERGE is taught as semantics and graded through SQLite's `INSERT ... ON CONFLICT` per the binding §5.3 note.

#### de-l7-iceberg-metadata - What Iceberg Solves: Snapshots, Manifests, and the Metadata Tree [medium] [~28 min]
- **Summary:** Explain what an open table format adds over raw Parquet in object storage and read Iceberg's snapshot and file metadata to see exactly what a query would scan.
- **Skills:** open table formats, ACID on object storage, snapshots, manifests, metadata tables, hidden partitioning, joins, NULL filtering.
- **Teach:** L6 ended at files plus a catalog equals a table, and its limits: no transactions, no safe concurrent writers, a frozen partition layout. Iceberg's answer is a metadata tree: the catalog points at a current snapshot, the snapshot points at manifests, manifests list data files with per-file stats; readers never list S3. Hidden partitioning and field-id schema evolution in one paragraph each; Delta and Hudi as a one-paragraph awareness note (Iceberg has the consumption gravity, §2.2). csdiagram: catalog -> snapshot -> manifest list -> manifests -> data files tree. Live demo: the current snapshot's live file set. "On a real platform": these seeds mirror the real `snapshots` and `files` metadata tables you query with `SELECT * FROM my_table.snapshots` in Spark or Athena. Interview nuance: the junior bar is the problem statement ("ACID, schema evolution, and time travel over Parquet in object storage, with a catalog pointer telling engines which files are current"), not spec internals.
- **Seeds:** `snapshots(snapshot_id, parent_id, committed_at, operation, added_files, deleted_files)` and `files(file_path, partition_dt, record_count, file_size_in_bytes, added_snapshot_id, deleted_snapshot_id)` (NULL deleted_snapshot_id = live), both named after Iceberg's real metadata tables.
- **Apply:** "Write a query that returns the live files a query on partition dt = '2026-07-01' would scan, as `(file_path, file_size_in_bytes)`, largest first." Single-file. Proves pruning is understood as metadata filtering, not magic.
- **Practice:** "Write a query that returns the table's commit history as `(snapshot_id, operation, added_files, deleted_files, committed_at)` in commit order." Single-file, light scaffold.
- **Extra practice:** find the snapshot that deleted the most files (medium); total live bytes vs total ever-written bytes (medium).
- **Interview rationale:** "What does Iceberg actually solve" is the standard junior lakehouse question; §2.2 defines the exact one-paragraph answer this lesson drills.

#### de-l7-upsert-merge-semantics - MERGE Semantics: Upserts That Survive a Rerun [hard] [~30 min]
- **Summary:** Implement warehouse MERGE semantics with INSERT ... ON CONFLICT DO UPDATE and prove the load is idempotent by running it twice.
- **Skills:** MERGE INTO semantics, upsert, ON CONFLICT DO UPDATE, natural keys, windowed dedup before merge, idempotent sinks, copy-on-write vs merge-on-read.
- **Teach:** MERGE INTO in one shape: match target rows on a key, update the matched, insert the rest; the model answer shows real Iceberg/warehouse MERGE syntax while the graded SQLite uses ON CONFLICT, the same semantics (stated plainly). Under the hood Iceberg executes it copy-on-write (rewrite affected files) or merge-on-read (deletion vectors, v3), a one-screen tradeoff. ### Module 8.2 - Idempotency, the Core Property (id: de-l8-idempotency)

#### de-l8-partition-replacement - Delete + Insert: Replacing the Run's Partition [medium] [~28 min]
- **Summary:** Write a batch load that owns exactly one date partition, driven by a run parameter instead of the wall clock, and prove it survives a rerun.
- **Skills:** idempotency, partition replacement, run parameterization, immutable data interval, DELETE scoped by predicate, INSERT...SELECT, multi-statement scripts.
- **Teach:** the simplest idempotent pattern that works everywhere (§5.3 implementation 1): DELETE the run's partition, INSERT it fresh. Open by naming the prior art out loud, because the learner has done the mechanic before: `sql-l5-incremental-watermark-backfill` hardcoded the partition date in the delete. The new idea here is that the date is a **parameter the orchestrator injects**, read from a `run_config` table and never from `datetime.now()`, because wall-clock leakage is the #1 DAG anti-pattern and it breaks reruns and backfills (§5.2); atomicity framing: the delete and insert are one unit, separate E/T/L into separate tasks; `csdiagram` pipeline diagram of batch -> delete dt -> insert dt; live demo over the demo seed: show the target before and after a double load without the delete (rows double). #### de-l8-late-data-audit - Late Data: Quantify the Silent Loss, Then Heal It [hard] [~28 min]
- **Summary:** Measure exactly how many rows a strict watermark load silently dropped, then repair the pipeline with a rolling reprocessing window that self-heals.

### Module 9.1 - Kafka Fundamentals (id: de-l9-kafka-fundamentals)

#### de-l9-log-topic-partition-offset - The Log: Topics, Partitions, and Offsets [medium] [~26 min]
- **Summary:** Explain the topic/partition/offset model and read partition depth and hot-partition skew off broker metadata with SQL.
- **Skills:** Kafka log model, partitions as parallelism unit, offsets, retention, hot-key skew, GROUP BY, MAX/AVG.
- **Teach:** An event stream is an append-only log; a topic is split into partitions (the unit of parallelism) and every record gets an immutable offset within its partition. csdiagram (pipeline/table hybrid): producers hashing a key onto 3 partitions, each partition an offset-numbered log. Retention deletes from the head, so log_start_offset moves; depth = log_end minus log_start. Partition-key choice decides both ordering (next module) and skew: one hot key means one hot partition. Live demo query: per-partition depth for `clickstream`, exposing partition 4 holding 9.4M messages vs ~800K elsewhere. Currency callout: Kafka 4.0 (March 2025) removed ZooKeeper entirely (KRaft only, controller failover under 5s); any tutorial mentioning ZooKeeper is pre-2025 and must not be repeated in an interview. Vendor prose: Kafka, Amazon MSK, Kinesis (shard = partition, sized for real in this module's closing lesson), Fabric Eventstreams.
- **Seeds:** `kafka_topics(topic, partitions, replication_factor, retention_hours)` with ('orders', 6, 3, 168), ('clickstream', 12, 3, 24), ('payments', 3, 3, 720), ('inventory_updates', 1, 3, 168); `topic_partitions(topic, partition_id, log_start_offset, log_end_offset, leader_broker)` mirroring `kafka-topics --describe` plus offset checker output, with clickstream partition 4 at log_end 9,400,000 while siblings sit near 800,000.
- **Apply:** "Write a query that returns each partition of the `clickstream` topic with the number of messages it currently retains, as (partition_id, message_count), fullest first." Single-file; expected set proves the learner computes depth as log_end_offset - log_start_offset, not raw log_end.
- **Practice:** "Write a query that returns every topic whose fullest partition holds more than twice its average partition depth, as (topic, max_depth, avg_depth)." Single-file; proves hot-partition detection via GROUP BY + MAX/AVG, the skew signal an on-call DE actually pulls.
- **Extra practice:** total messages retained per topic, largest first (easy); partitions whose leader sits on broker 2, with depth (easy); each topic's retention_hours next to its total depth to reason about replay window (medium).
- **Interview rationale:** "Explain topics, partitions, and offsets" is the opening Kafka question in intern loops (RESEARCH §5.6); hot-key skew is called out there as junior-reachable.

#### de-l9-consumer-groups-lag - Consumer Groups and Measuring Lag [medium] [~28 min]
- **Summary:** Explain consumer-group partition ownership and compute per-partition and per-group consumer lag exactly the way the CLI does.
- **Skills:** consumer groups, committed offsets, consumer lag, rebalancing, JOIN, GROUP BY, conditional flags.
- **Teach:** Deepen-not-repeat note, stated to the learner: sql-l5's system-design-reasoning lesson introduced consumer lag as a vocabulary item; what is new here is the exact formula, the metadata it comes from, and rebalancing mechanics. A consumer group divides a topic's partitions among members; each partition is owned by exactly one member at a time. The committed offset is the NEXT offset to read, and lag = log_end_offset - committed_offset, the one formula this lesson drills. csdiagram: two consumers of a group each owning partitions with committed markers trailing log-end. Rebalancing: when a member leaves, its partitions are reassigned; during the shuffle `member_id` is empty and processing pauses (KIP-848 incremental rebalances shrink that pause, prose callout). Live demo: join `consumer_group_offsets` to `topic_partitions` and reproduce the `kafka-consumer-groups --describe` columns (CURRENT-OFFSET, LOG-END-OFFSET, LAG). Interview nuance: lag is a rate race, not a number; a big-but-shrinking lag is a recovering consumer, a small-but-growing one is falling behind.
- **Seeds:** reuse `topic_partitions`; `consumer_group_offsets(group_id, topic, partition_id, committed_offset, last_commit_ts_ms, member_id)` with `member_id = ''` on two mid-rebalance rows and a `fraud-detector` group whose last_commit_ts_ms froze 40 minutes ago on `payments`.
- **Apply:** "Write a query that returns the lag on every partition of `payments` for the `fraud-detector` group, as (partition_id, committed_offset, log_end_offset, lag), biggest lag first." Single-file; expected set proves the join and the subtraction.
- **Practice:** "Write a query that returns each consumer group with its total lag across all partitions and a `stalled` flag of 1 when it has lag but no commit in the last 15 minutes (now is 1767290400000 ms), as (group_id, total_lag, stalled), worst first." Single-file; proves aggregation plus the freeze heuristic an alert would encode.
- **Extra practice:** partitions currently owned by nobody, i.e. member_id '' (easy); the group with the single worst per-partition lag (medium); per group, the fraction of its partitions with zero lag, rounded to 2 decimals (hard).
- **Interview rationale:** "How do you measure consumer lag" is quizzed verbatim (RESEARCH §5.6: lag = log-end minus committed); the stalled-group query is the production monitoring twin.

#### de-l9-delivery-semantics - Delivery Semantics: What Each Guarantee Costs [hard] [~28 min]
- **Summary:** Derive at-most-once vs at-least-once from commit ordering and identify, from crash-time metadata, exactly which messages get lost vs redelivered.
- **Skills:** at-most/at-least/exactly-once, offset-commit ordering, crash recovery, producer idempotence, JOIN, range predicates.
- **Teach:** Delivery semantics are nothing but commit ordering: commit BEFORE processing = at-most-once (a crash between commit and process loses messages); commit AFTER = at-least-once, Kafka's default posture (a crash between process and commit redelivers them). csdiagram: timeline of process/commit interleavings with a crash bolt, one lane per semantic. Exactly-once needs transactions plus read_committed and is senior awareness; what a junior must recite is the sentence this whole level builds toward: true exactly-once delivery is impossible, at-least-once delivery plus an idempotent sink is effectively exactly-once. Producer side in prose: enable.idempotence kills resend duplicates, acks trades latency vs durability. Live demo: reconstruct one group's crash from the two metadata tables.
- **Seeds:** `processing_attempts(group_id, partition_id, message_offset, processed_ok, processed_at_ms)` and `consumer_commits(group_id, partition_id, committed_offset, commit_ts_ms)`; group `order-enricher` commits after processing (some processed offsets above its committed offset at crash time 1767290400000), group `email-blaster` commits before (committed offsets it never processed).
- **Apply:** "Write a query that returns, for the `order-enricher` group, the messages that will be delivered a second time after the crash, as (partition_id, message_offset), in order." Single-file; expected set proves the learner ranges over offsets >= committed_offset that were already processed_ok, i.e. understands committed = next-to-read.
- **Practice:** "Write a query that returns the messages the `email-blaster` group lost forever, as (partition_id, message_offset, committed_offset)." Single-file, minimal hints; proves the at-most-once loss window is committed-but-never-processed.
- **Extra practice:** count of duplicate-to-be deliveries per partition for order-enricher (medium); which of the two groups can safely feed a bank ledger, answered as a query returning the group whose crash produced zero lost messages (hard).
- **Interview rationale:** RESEARCH §5.6 calls the commit-ordering derivation "crisp and gradable"; the at-least-once + idempotent-sink sentence is the interviewer-grade answer (finding 6) and this lesson makes the learner earn it from data.

#### de-l9-kinesis-shard-math - Kinesis: Shard Math, Firehose Buffers, and the Chooser [medium] [~28 min]
- **Summary:** Size a Kinesis stream with graded shard arithmetic, explain why Firehose is near-real-time by construction, and choose between Streams, Firehose, and MSK from workload requirements. (New lesson per the repeat audit: Kinesis was prose-only despite appearing in two-thirds of AWS-flavored loops; implication 21 mandates exactly these three graded pieces.)
- **Skills:** Kinesis shards, per-shard throughput limits, capacity sizing, ceiling integer arithmetic, Firehose buffering, Streams vs Firehose vs MSK, CASE ladders.
- **Teach:** The shard = partition mapping from 9.1.1 now gets numbers. Per-shard hard limits: 1 MB/s or 1,000 records/s on write, 2 MB/s on read (enhanced fan-out gives each consumer its own 2 MB/s, prose callout). Shards needed = the CEILING of the LARGER of the two constraints, and both matter: a small-record firehose of events maxes records/s long before MB/s. Constraint note, resolved in favor of the platform: SQLite has no CEIL function, so ceiling division is spelled with the integer idiom (x + 999) / 1000 after computing throughput in KB/s (1 MB = 1000 KB stated in the prompt), and teaching that idiom is itself interview-transferable. Firehose is not a queue you read; it is a delivery hose that buffers by size OR interval, whichever fills first (e.g. 5 MB or 300 s), so its latency floor is the buffer interval at low throughput: "near-real-time" is a buffering fact, not marketing. The chooser, taught as a precedence ladder: Kafka-API compatibility or ecosystem lock-in means MSK; replay or multiple custom consumers means Kinesis Data Streams; plain delivery into S3/Redshift with light transform means Firehose. Flink placement in prose: stateful processing on AWS runs on Amazon Managed Service for Apache Flink (see 9.3.2 for the checkpointing/backpressure vocabulary). Live demo: the shard computation for one workload, both constraints side by side. csdiagram: one stream fanning into shards with the two limit gauges per shard.
- **Seeds:** `stream_workloads(workload, records_per_sec, avg_record_kb, consumer_count, needs_replay, needs_kafka_api, sink)` with 7 rows engineered so both constraints bind somewhere: clickstream (5,000 rec/s, 2.0 KB: MB/s binds at 10 shards), iot_telemetry (12,000 rec/s, 0.3 KB: records bind at 12 shards), payments (800 rec/s, 1.5 KB: naive integer division says 1, ceiling says 2), audit_log (200 rec/s, 4.0 KB: 1 shard), plus one Kafka-API workload and two Firehose-shaped S3 loaders.
- **Apply:** "Write a query that returns each workload with the shards it needs, as (workload, kb_per_sec, records_per_sec, shards_needed), most shards first, where shards_needed is the larger of the throughput and record-count requirements, rounded up." Single-file; expected set proves the max-of-two-constraints logic and the ceiling (payments fails under naive division, iot_telemetry fails if only MB/s is checked).
- **Practice:** "Write a query that returns each workload's recommended service, as (workload, recommended_service), using this precedence: Kafka-API compatibility required means 'msk'; else replay needed or more than one consumer means 'kinesis_streams'; else 'firehose'." Single-file; proves the CASE ladder's precedence ordering, the exact shape of the interview chooser answer.
- **Extra practice:** total shards across the portfolio (easy); for each Firehose workload, whether a 5 MB / 300 s buffer flushes on size or on time at its throughput, i.e. its worst-case delivery delay (hard); shards_needed after 30% growth and which workloads change (medium).
- **Interview rationale:** RESEARCH finding 4: Kinesis features in ~67% of AWS-flavored DE loops; implication 21 mandates shard math as graded numeric exercises plus the Firehose-buffering and Streams-vs-Firehose-vs-MSK decisions. #### de-l9-ordering-guarantees - Ordering and Checkpoints: Out-of-Order Arrival and the Bounded Apply [hard] [~32 min]
- **Summary:** State what ordering Kafka does and does not promise, detect out-of-order arrivals with LAG, and write the lsn-ordered, checkpoint-bounded, idempotent apply that survives shuffled input and reruns. (Absorbs the cut de-l9-apply-changelog per the repeat audit; the lsn-bounded checkpoint with an apply_watermark table is the genuinely new content and lives here.)
- **Skills:** per-partition ordering, partition-key choice, out-of-order detection, LAG, log-position apply, INSERT ... ON CONFLICT DO UPDATE, tombstone delete, apply_watermark checkpoint, workspace scripting.
- **Teach:** Kafka guarantees order WITHIN a partition, nothing across partitions. Key the events by the primary key and all changes for one row land in one partition, in order; key them by anything else (or merge two topics) and arrival order can invert log order for a key. csdiagram: two keys interleaved across two partitions, arrival sequence vs lsn sequence diverging, with a watermark line marking the checkpoint. The fix is never "hope": sort by lsn (or source transaction id) at apply time, because arrival_seq is an accident and lsn is the truth. The apply discipline in three moves: reduce to the latest event per key by lsn, delete the keys whose latest op is 'd', upsert the rest. MERGE is the name interviewers expect (Snowflake, BigQuery, Athena-on-Iceberg spell this `MERGE INTO`); SQLite has no MERGE keyword, so the same semantics are written as `INSERT ... ON CONFLICT (key) DO UPDATE`, and "MERGE is an upsert plus a delete branch" IS the understanding (platform constraint upheld). The upsert mechanics themselves were graded in L8 on a plain redelivered batch, so they are composed here, not re-taught. What is new: bounding the apply by log position. A restartable consumer applies events with lsn <= checkpoint, records how far it got in `apply_watermark(last_lsn)`, and resumes from there next run; at-least-once delivery means the same slice WILL arrive twice, and `checkIdempotency` grades that harmlessness literally. Live demo: LAG over arrival order exposing the inversions. Interview nuance: "how do you guarantee ordering in Kafka" has a two-word core answer, partition key, and the follow-up "and what if it is already shuffled" is answered by ordering on the log position at the sink.
- **Seeds:** `cdc_events(lsn, arrival_seq, ts_ms, op, order_id, after_status)` for an `orders` source keyed (wrongly) by warehouse_id: 20 events where order 1042's 'shipped' (lsn 1207) arrives before its 'packed' (lsn 1201), one order whose final event is op 'd' (cancelled and purged, exercising the delete branch), and a brand-new order first seen mid-stream; `orders(order_id PRIMARY KEY, status)` preloaded; `apply_watermark(last_lsn)` empty.
- **Apply:** "Write a query that returns every event that arrived out of log order for its key, as (order_id, lsn, arrival_seq), in arrival order." Single-file; expected set proves LAG(lsn) partitioned by order_id ordered by arrival_seq catches exactly the inversions.
- **Practice:** "Write a script that applies only the events with lsn <= 1210 (a mid-stream checkpoint) to `orders`: latest event per order wins in log order, op 'd' deletes, everything else upserts with INSERT ... ### Module 9.3 - Stream Processing in SQL (id: de-l9-stream-processing-sql)

#### de-l9-tumbling-hopping-windows - Tumbling and Hopping Windows [medium] [~26 min]
- **Summary:** Bucket an event stream into tumbling windows with epoch arithmetic and into overlapping hopping windows with a window-table join.
- **Skills:** tumbling windows, hopping windows, event-time bucketing, epoch arithmetic, GROUP BY, range joins.
- **Teach:** Deepen-not-repeat note, stated to the learner: sql-l5's system-design-reasoning lesson introduced tumbling windows as vocabulary; what is new here is implementing them, the half-open bounds, and hopping windows, which L5 never touched. A window turns an infinite stream into finite groups. Tumbling: fixed size, no overlap; every event belongs to exactly one bucket, computed as (event_time_ms / 300000) * 300000 for 5 minutes, integer division doing the flooring. Hopping: size 10 min, hop 5 min; every event belongs to two windows, which no single GROUP BY expression can produce, so you join events against a table of window bounds, exactly how a stream engine's operator state is shaped. csdiagram: one event timeline sliced twice, tumbling lane and overlapping hopping lane. Session windows get their own drill. Live demo: the tumbling bucket expression next to raw event_time_ms. Vendor prose: Flink, Spark Structured Streaming, Amazon Managed Service for Apache Flink (the 2023 rename of Kinesis Data Analytics; the old name still circulates in prep material and should not be repeated in an interview), and DP-700's Eventstreams all speak these three window words.

#### de-l9-watermarks-late-events - Event Time, Watermarks, and Late Events [hard] [~28 min]
- **Summary:** Separate event time from processing time, apply a watermark to decide which events count as late, and quantify what late data does to already-closed windows.
- **Skills:** event time vs processing time, watermarks, allowed lateness, late-event policy, conditional aggregation, CASE.
- **Teach:** Every event has two clocks: when it happened (event_time_ms) and when the pipeline saw it (processing_time_ms), and mobile clients, retries, and network partitions drive them apart. Flink awareness callout (§5.6, one prose paragraph, not graded): checkpointing is Flink's periodic consistent snapshot of operator state (barriers flow with the stream; recovery restarts from the last checkpoint, which is what makes its exactly-once state claim true), and backpressure is a slow operator forcing upstream stages to throttle, visible from the outside as growing consumer lag; a junior needs the two words, not the internals. Live demo: lateness = processing_time_ms - event_time_ms per event. Interview nuance: "where do late events go" is asked exactly that openly; naming all four options with a tradeoff each is the strong answer.

- **Practice:** "Write a query that returns each 5-minute tumbling window whose final count differs from its on-time count (events arriving within the watermark), as (window_start_ms, on_time_count, final_count)." ### Module 10.2 - Shuffle, Skew & Tuning (id: de-l10-shuffle-skew-tuning)
Four lessons that go from "the shuffle exists" (L6) to tuning it: which operations force a shuffle and when to buy your way out of one by broadcasting, partition-count arithmetic, percentile-based skew diagnosis, caching judgment, and the Amazon slow-job capstone.

#### de-l10-narrow-wide-and-broadcast - Narrow, Wide, and the Broadcast Decision at 10 MB and 100 MB [medium] [~28 min]
- **Summary:** Separate narrow from wide stages using shuffle metrics rather than operator names, pick auto-broadcast, hinted broadcast, or sort-merge for each join with the real byte thresholds, and flag the stages whose shuffle write crosses the 10 GB line.
- **Skills:** narrow vs wide transformations, shuffle as the dominant cost, broadcast vs sort-merge join, autoBroadcastJoinThreshold 10 MB, the ~100 MB manual ceiling, driver memory as the broadcast budget, AQE runtime broadcast conversion, shuffle-volume triage, CASE classification, JOIN.
- **Teach:** Opens by naming what is already yours: L6 taught the narrow/wide split and graded the binary "is this dimension under 10 MB" flag, so neither is re-taught here. What is new is the band and the bet. Narrow vs wide read from metrics: a stage with no shuffle read is fed narrowly and pipelines with its neighbors, a stage with shuffle read sits downstream of a wide step, and the shuffle write belongs to the producing stage (the L6 attribution rule, now used as a diagnostic rather than a fact). The broadcast band: under `spark.sql.autoBroadcastJoinThreshold` (10 MB, exactly 10485760 bytes) the engine broadcasts without being asked; between that and roughly 100 MB you can force it with a broadcast hint, and that is a judgment call, not a free win, because the small side is collected to the driver first and then copied to every executor, so a forced broadcast spends driver memory and network on every task slot; above roughly 100 MB the sane answer is sort-merge, and forcing it anyway produces the driver OOM from lesson one. AQE moves the line at runtime: a side the planner estimated at 500 MB can arrive post-filter at 8 MB, and AQE converts sort-merge to broadcast then, which is why plan-time strategy and the strategy in the UI disagree and why "check what actually ran" is the senior-sounding follow-up. Then the 10 GB line: §5.8's shuffle-heavy-stage query. A join stage writing more than 10 GB of shuffle is the physical evidence behind the design-time heuristic `de-l7-kimball-vs-obt` states as "keep the star while the join side stays under roughly 10 GB", so when this query returns rows, the conversation moves from tuning to modeling (pre-join into an OBT, or co-locate on a distribution key). csdiagram: table mapping join shape to engine choice to data movement to the failure mode when you force the wrong one. Live demo: the join candidates next to their computed small side and chosen strategy. On a real platform this differs: Redshift expresses the same decision as DISTSTYLE ALL for small dimensions. Interview nuance: candidates who say only "broadcast the small table" get a follow-up on how small, and the strong answer is 10 MB automatic, up to about 100 MB by hint if the driver can hold it, sort-merge past that.
- **Seeds:** `join_candidates(join_id, left_table, left_size_bytes, right_table, right_size_bytes, planned_strategy, actual_strategy)` including one AQE-converted join where planned and actual disagree and one over-100 MB side; `spark_stages(stage_id, job_id, name, shuffle_read_mb, shuffle_write_mb, num_tasks)` with two stages over 10 GB of shuffle write; `cluster_config(setting, value)` carrying ('spark.sql.autoBroadcastJoinThreshold','10485760') and ('spark.driver.memory','4096').
- **Apply:** "Write a query that returns the join strategy each join should use, as (join_id, small_side_mb, strategy), where strategy is 'auto_broadcast' when the smaller side is under 10485760 bytes, 'hint_broadcast' from there up to 104857600 bytes, and 'sort_merge' above that, smallest small side first." Single-file, assertColumnNames; the learner must derive the small side with MIN over the two size columns instead of reading a pre-labeled dimension row, then apply both cutoffs. Proves the Tier B numbers as arithmetic on both ends of the band.
- **Practice:** "Write a query that returns the shuffle-heavy stages a modeling change would target: every stage writing more than 10 GB of shuffle, with its shuffle write in GB and its share of the job's total shuffle write, as (stage_id, shuffle_write_gb, pct_of_job_shuffle), biggest first." Lean starter, two hints only. Proves the §5.8 query that hands the learner the evidence for the Kimball-vs-OBT argument L7 makes at design time.
- **Extra practice:** count of stages with zero shuffle read, the narrow-fed ones (easy); the joins where planned_strategy and actual_strategy disagree, the AQE conversions (medium); the joins whose smaller side would consume more than a quarter of `spark.driver.memory` if broadcast (hard, requires casting the config value).
- **Interview rationale:** Tier A narrow vs wide plus Tier B broadcast thresholds (§5.8); implication 32 requires 10MB and ~100MB baked into grading, and §5.8 names the "shuffle_write exceeds 10GB" query as the one that grounds the Kimball-vs-OBT heuristic the course already teaches. L6 graded only the binary under-10-MB flag, so the band, the driver bet, and the 10 GB read are all first-time grading here.

#### de-l10-shuffle-partition-count - Shuffle Partition Count: Why 200 Is Wrong for Your Job [medium] [~26 min]
- **Summary:** Reason about spark.sql.shuffle.partitions with the 2-4 per core heuristic, spot over- and under-partitioned stages from task metrics, and state what AQE now does automatically.
- **Skills:** spark.sql.shuffle.partitions default 200, 2-4 partitions per core, repartition vs coalesce, AQE partition coalescing, CROSS JOIN with a config table, CASE classification.
- **Teach:** The default 200 is wrong twice: tiny data gets 200 near-empty tasks whose scheduling overhead dominates; huge data gets giant tasks that spill and OOM. The heuristic: 2-4 partitions per total core. repartition (shuffles, either direction) vs coalesce (no shuffle, only down). AQE coalesces small post-shuffle partitions automatically, default since Spark 3.2 / Glue 4.0; answers that omit AQE read as 2019-era. Spark 4.0 currency note in prose (ANSI mode fail-fast). Live demo: cluster_config next to per-stage avg-MB-per-task.
- **Seeds:** `cluster_config(setting, value)` including ('spark.sql.shuffle.partitions','200'); `spark_executors(executor_id, cores)`; `spark_stages(stage_id, name, num_tasks, shuffle_read_mb)`; `spark_tasks(task_id, stage_id, duration_ms, spill_mb)`.
- **Apply:** "Write a query that returns the cluster's recommended shuffle-partition range and the configured value, as (total_cores, low_recommendation, high_recommendation, configured)" using 2x and 4x total cores against cluster_config. Single-file. Proves the heuristic as arithmetic, with the hard numbers graded.
- **Practice:** "Write a query that classifies each stage as over_partitioned, under_partitioned, or ok, as (stage_id, avg_mb_per_task, verdict)", using thresholds under 1 MB and over 1000 MB per task. Proves metric-based tuning judgment.

- **Interview rationale:** "Your job runs 200 tasks on an 8-core cluster, what do you change" is Tier B verbatim (§5.8); implication 32 requires 200 and 2-4/core hard-coded into grading.

#### de-l10-diagnosing-skew - Skew Diagnosis with Percentiles: Max vs Median, Not Max vs Mean [hard] [~28 min]
- **Summary:** Compute median and percentile task durations in SQL, apply the max-over-median skew signal and AQE's 5x-median rule, and name the fix ladder.
- **Skills:** data skew diagnosis, median via ROW_NUMBER, percentiles in SQL, AQE skew-join rule, salting, spill as corroborating signal, window functions.
- **Teach:** L6's own caveat becomes the lesson: the straggler drags the mean up, so max-over-mean understates skew; the interview-cited signal is max task time vs MEDIAN task time. Computing a median in SQLite with ROW_NUMBER + COUNT (no percentile function, which is the point: you can do this anywhere). AQE splits a skewed partition when it is over 5x the median AND over 256 MB. - **Practice:** "Write a query that returns the stages AQE would flag for skew-join splitting, as (stage_id, max_over_median, max_partition_mb)", applying both the over-5x-median and over-256 MB conditions. Lean starter. Proves the modern default answer with its real thresholds.
- **Extra practice:** count of spilling tasks per stage (easy); the partition holding over 30% of a stage's rows, the hot key (medium); p90 task duration per stage via ROW_NUMBER math (hard).
- **Interview rationale:** "One task took 40 minutes, the median was 2, diagnose" is the detection half of the Amazon question (§5.8, implication 31); the max-vs-median signal is cited verbatim across every interview corpus.

### Module 10.3 - Data Quality & Observability (id: de-l10-quality-observability)
Where quality results GO and how production watches them. Deliberately scoped by the Level 8 review's ownership split: Level 8 owns the dbt test vocabulary (unit vs data tests, a test is a query returning violating rows that passes at zero, the violation list as the expected set) and SQL Level 5 `sql-l5-data-quality-gates` already grades the write-audit-publish blocking gate, so this module cross-references both and rebuilds neither. There is no publish-clean-rows / quarantine-with-a-reason workspace here. What this module owns instead: the append-only check_results ledger with warn-vs-error severity, the five observability pillars as always-on monitors over metadata, schema-drift detection, and lineage-driven incident triage.

#### de-l10-check-suites - From One Check to a Severity-Ranked Check Ledger [medium] [~28 min]
- **Summary:** Run a whole check suite in one script, record every result in an append-only check_results ledger with its severity, and derive the run verdict from severity rather than from a raw failure count.
- **Skills:** check suites, the check_results ledger, warn vs error severity, run verdict, append-only history vs current status, multi-statement SQL scripts, scoped idempotency.
- **Teach:** L6 ran checks one query at a time, and L8 taught the vocabulary those checks are written in (a test is a query returning violating rows and it passes at zero rows; unit tests fixture-test logic in CI, data tests run every load). Neither stores a result, and a check whose result is not stored can only answer "is it broken now". Production keeps a ledger: `check_results(run_id, check_name, table_name, failed_rows, severity, status, checked_at)`, appended every run, plus `dq_check_status` holding exactly one current row per check for the dashboard. Severity is the operational half interviews probe and the half no earlier level grades: warn records and pages nobody, error blocks the load, and the same failing check can be a warn in dev and an error in prod, which is why severity is a property of the check definition rather than of the query. What "blocks the load" actually looks like in SQL is the write-audit-publish gate SQL Level 5 already grades (stage, audit, publish only on a clean pass); this lesson points at it and stays on the ledger and the verdict, so the course grades that gate exactly once. Because the ledger is append-only it answers the questions a boolean cannot: has this check ever passed, when did it start failing, is this the third night in a row. csdiagram: table mapping severity to what it does to the run and who hears about it. Live demo: two checks writing their ledger rows, then the status refresh. On a real platform this differs: dbt stores this in `run_results.json`, Great Expectations in validation results, Soda in a check history table, all the same two shapes. Interview nuance: "how do you know your data is correct" is answered with the check families (L6) plus where the results land and who gets woken up (here); candidates who stop at "I write tests" get the follow-up.
- **Seeds:** `staged_orders(order_id, customer_id, amount, status, order_date)` with planted defects (duplicate order_id, NULL customer_id, negative amount, orphan customer_id) plus `customers(customer_id, region)` and `check_definitions(check_name, table_name, severity)` naming the four checks, two 'error' and two 'warn'; empty `check_results` and `dq_check_status`. The practice adds a pre-seeded `check_results` holding four prior runs so a verdict can be computed per run.
- **Apply:** "Write a script that runs the four checks in check_definitions against staged_orders and appends one check_results row per check for run 'run_2026_03_02', carrying each check's failed_rows, its severity taken from check_definitions, and a status of pass or fail, then refreshes dq_check_status to hold exactly one current row per check." Workspace script; hidden assertions verify each check's failed_rows, that severity came from the definition table rather than being hardcoded, and that dq_check_status has one row per check. Grading: `checkIdempotency: true` WITH `idempotencyTables: ['dq_check_status']`. This is mandatory, not optional: `check_results` is an append-only ledger that grows by design on every run, so a bare `checkIdempotency` (which compares whole-workspace state) would fail every correct solution. - **Practice:** "Write a query that returns the verdict for each run in the ledger, as (run_id, error_failures, warn_failures, verdict), where verdict is 'blocked' when any error-severity check failed, 'warn' when only warn-severity checks failed, and 'passed' otherwise, newest run first." Proves that severity decides the verdict, not the raw failure count, which is the distinction the module owns.
- **Extra practice:** count of checks by severity in check_definitions (easy); the checks that have never recorded a pass anywhere in the ledger (medium); the current consecutive-failure streak per check via window functions (hard).
- **Interview rationale:** "How do you know your data is correct" at the depth §5.7 says interviews now expect. The vocabulary half is graded in Level 8 and the blocking gate in SQL Level 5, so this lesson is scored on what neither reaches: results with severity, a history you can query, and a verdict derived from severity.

#### de-l10-observability-pillars - The Five Pillars: Freshness and Volume Monitors in SQL [medium] [~28 min]
- **Summary:** Name the five observability pillars and implement freshness, volume, and distribution monitors over table metadata.

#### de-l11-similarity-search - The Similarity Query Demystified: Top-k Cosine in Plain SQL [medium] [~27 min]
- **Summary:** Learner can compute top-k cosine similarity over a seeded low-dimension embedding table in plain SQL and explain that a vector store's core query is this ranking plus an index that avoids the full scan.
- **Skills:** cosine similarity, dot products in SQL, top-k retrieval, magnitude vs direction, ANN concept (HNSW/IVF as scan avoidance), JOIN on dimension, GROUP BY, ROUND, LIMIT
- **Teach:** The demystification lesson (research implication 35): everything a vector store does at query time is one SQL-expressible ranking, SELECT chunks ORDER BY similarity DESC LIMIT k; HNSW and IVF indexes exist only to avoid scanning every row, the same reason B-trees exist. Cosine similarity is the dot product of the two vectors divided by the product of their norms: direction, not magnitude. Real embeddings are 1,536-dim floats; the lesson uses 4-dim small-integer vectors so every dot product is hand-checkable, and the expected set ROUNDs the score so grading is not floating-point-fragile. One seeded chunk has deliberately large components: it wins the raw dot-product ranking but loses on cosine, the magnitude trap made visible. Live demo: the full ranked cosine list against the query vector. Constraint note: L2 norms ship precomputed in a seed table because the platform's sql.js SQLite build has no SQRT function; this matches reality, since production vector stores precompute and cache norms too.
- **Seeds:** `query_vector(dim, component)`; 4 rows, small integer components in -3..3. `chunk_embeddings(chunk_id, dim, component)`; 8 chunks x 4 dims = 32 rows, small integers, one high-magnitude chunk (components near 9) engineered to top the dot product but not the cosine ranking. `embedding_norms(vec_id, l2_norm)`; precomputed L2 norms for 'query' and every chunk (precomputed per the no-SQRT constraint above). Simulates a pgvector table flattened to components plus its norm side-table, the honest small-scale model of the store module 11.1 built.
- **Apply:** "Write a query that returns the 3 chunks most similar to the query vector by cosine similarity, as (chunk_id, cosine_sim), rounded to 3 decimals, most similar first." Single-file, orderMatters + assertColumnNames, LIMIT 3. Proves the learner can write the exact query a vector store answers.
- **Practice:** "Write a query that returns every chunk's raw dot product and cosine similarity side by side, as (chunk_id, dot_product, cosine_sim), highest cosine first." Lighter scaffold. Proves magnitude-vs-direction: the high-magnitude chunk leads one column and not the other.
- **Extra practice:** each chunk's dot product with the query vector only (easy); the nearest neighbor of a given chunk, chunk-to-chunk cosine over the same seeds (hard).
- **Interview rationale:** "What actually happens when you query a vector database?" separates candidates who recite vendor names from candidates who can write the naive k-NN scan and then explain what HNSW approximates; having computed it by hand is what makes the parameter-dropping (1,536 dims, top-k, recall) credible per research 4.6.

#### de-l11-embedding-freshness - The RAG Freshness Problem: Stale Vectors Fail Silently [medium] [~28 min]
- **Summary:** Learner can detect the three staleness sources in a vector index with SQL: source-document drift, mixed embedding-model generations, and recall decay over time.
- **Skills:** embedding freshness, model-generation compatibility, freshness SLAs, rebuildable-cache framing, date comparison, JOIN, GROUP BY HAVING, self-audit queries
- **Teach:** Stale embeddings fail with no alert: documented recall drift 0.92 to 0.74 (research 4.1). - **Extra practice:** the per-category stale rollup as (category, stale_chunks), the aggregate view of the apply's row-level set (medium); oldest embedded_at per category (easy); weeks where recall_at_5 dropped vs the prior week using a self-join or window (hard).

#### de-l11-incremental-reembed - Incremental Re-Embedding as an Idempotent Pipeline [hard] [~32 min]
- **Summary:** Learner can write a delete+insert re-embedding script that refreshes only changed documents and survives being run twice, the L8 idempotency pattern pointed at a vector sink.

- **Interview rationale:** "How would you know your pipeline silently broke?" is a stock reliability question (research 5.7); this arms it with the AI-curation instance plus a reusable LAG pattern.

### Module 11.4 - Semantics, Text-to-SQL & the AI-Era Role (id: de-l11-semantics-role)
The semantic model as the text-to-SQL accuracy lever, graded by making the learner the human in the loop: implement the governed metric, then catch and correct a plausible-but-wrong AI query. Closes the level and the course arc with the commoditize-vs-appreciate framing.

#### de-l11-semantic-models - Semantic Models: the Text-to-SQL Accuracy Lever [medium] [~29 min]
- **Summary:** Learner can read a semantic contract (metric definitions, filters, join paths) and implement its metrics exactly, understanding why this artifact moves AI accuracy more than any model upgrade.
- **Skills:** semantic layers, governed metric definitions, metric drift, join-path contracts, text-to-SQL grounding, SUM with filters, JOIN per contract, date truncation
- **Teach:** The numbers that make the case (research 4.4): dbt's Apr 2026 benchmark lifted Claude Sonnet 4.6 from 90.0% to 98.2% and GPT-5.3-Codex from 84.1% to 100% with semantic-layer grounding, while raw text-to-SQL crawled from 32.7% (2023) to 64.5% (2026); Spider 2.0's agent scored 91.2% academic vs 21.3% enterprise-realistic; Snowflake's Cortex Analyst went 57% to 78% on BIRD-SQL with a semantic model. What the DE authors: logical tables, dimensions, metrics with exact filters, predefined join paths, verified queries; OSI v1.0 (Jan 2026, Snowflake-led with dbt/Databricks/Microsoft) named in a prose callout. Metric drift ("same question, different revenue numbers") is the failure the contract kills. Live demo: the contract table itself, queried.
- **Seeds:** `orders(order_id, customer_id, order_dt, status, gross_usd, refund_usd)`; ~14 rows with statuses 'complete'/'cancelled'/'pending' and nonzero refunds. `semantic_metrics(metric_name, grain, definition, required_filter)`; rows like ('net_revenue', 'monthly', 'SUM(gross_usd - refund_usd)', "status = 'complete'"). Simulates a dbt-style semantic model compiled to a metadata table.
- **Apply:** "Write a query that returns monthly net_revenue exactly per the semantic contract, as (month, net_revenue), using strftime for the month grain, complete orders only, gross minus refunds." Single-file, orderMatters + assertColumnNames. Proves contract-faithful implementation; the expected set is the ground truth lesson 12 reuses.
- **Practice:** "Write a query that returns monthly active_customers per the contract's definition (distinct customers with a complete order in the month), as (month, active_customers)." Lighter scaffold. Proves a second contract read.
- **Extra practice:** the drift demo: net vs gross revenue side by side per month (medium); cancelled-order refund exposure (easy).
- **Interview rationale:** Finding 3 says only 5% of teams have semantic models while 89% report modeling pain; being the junior who can author and implement metric contracts is the appreciating skill the research names.

#### de-l11-reviewing-ai-sql - Reviewing AI-Written SQL, and What Appreciates in the AI Era [hard] [~31 min]
- **Summary:** Learner can review a syntactically perfect AI-written query against a semantic contract, name its semantic bugs, and prove the divergence with SQL, then articulate what commoditizes vs appreciates in the DE role.
- **Skills:** AI-SQL review judgment, semantic vs syntax errors, fan-out detection, metric contract enforcement, discrepancy queries, EXCEPT/comparison patterns, human-in-the-loop rigor
- **Teach:** 81.2% of text-to-SQL failures are schema/semantic, not syntax: "correct syntax, wrong meaning" (research 4.4). The teach shows a real AI-shaped wrong answer against lesson 11's schema: it joins order_items, fanning out gross_usd per line item, forgets the status filter, and reports gross instead of net; every line parses, every number is wrong. Review checklist taught as the durable skill: check the grain, check the filters, check for join fan-out, check against the metric contract. Then the honest role close (finding 7 + 4.5): codegen is commoditizing (dbt Copilot, Databricks Genie in prose); modeling, quality, cost governance, and review judgment are appreciating; 72% of orgs want AI-assisted coding but only 24% trust it to manage pipelines, and trust is built from reasoning traces, evals, and human-in-the-loop checkpoints, which is more engineering rigor, not less. Reprise of the level-intro framing: none of this is intern-core yet; all of it compounds.
- **Seeds:** `orders` as lesson 11 plus `order_items(order_id, item_id, item_usd)`; ~10 item rows engineered so the fan-out inflates revenue visibly (a 3-item order triples). `semantic_metrics` carried over. The AI's wrong query appears in teach markdown only, never as starter code.
- **Apply:** "Write the corrected query the AI should have written: monthly net_revenue per the contract, unaffected by order_items fan-out, as (month, net_revenue)." Single-file; expected set matches lesson 11's ground truth, proving the learner reproduced the contract despite the tempting join.
- **Practice (level-end, unscaffolded):** "Write a query that proves the AI query is wrong: return each month where the AI's fanned-out gross number diverges from the contract's net_revenue, as (month, ai_revenue, contract_revenue, diff_usd)." Bare starter, no hints; the learner must reconstruct the AI's logic in a CTE and diff it against their own. Goal-state, the course's closing exercise.
- **Extra practice:** count of orders whose item sum disagrees with gross_usd (hard).
- **Interview rationale:** "Here is a query our AI assistant wrote, review it" is entering loops at AI-forward companies, and the fan-out-plus-filter miss is the exact bug class Omni's 81.2% stat describes; the review checklist transfers to every code-review round.
