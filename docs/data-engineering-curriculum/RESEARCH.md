# Data Engineering in the Age of AI — Research Brief (2026-08)

**Purpose.** This document is the single canonical research grounding for the design of a 100+ lesson, browser-based, hands-on, interview-prep-focused Data Engineering curriculum (SQL becomes one section; new sections cover cloud/AWS, pipelines/orchestration/streaming, data modeling, and AI-era DE). It merges five research lenses (landscape, AWS/cloud, AI-era, pipelines, interview signal, pedagogy/UX) researched July-August 2026, plus three gap-fill lenses integrated August 2026 (Spark/distributed compute, Azure/Fabric demand reconciliation, DataFrame tooling). Where lenses disagreed, the resolution and its rationale are stated inline.

**Platform constraints assumed throughout:** everything runs client-side (sql.js for SQL, Pyodide for Python, the shipped free-response design engine for open-ended answers), and the proven pedagogical device is "query the platform's simulated metadata" (already shipped for SQL Level 6 cloud foundations).

## 1. Executive Summary: the 13 findings that most shape the curriculum

1. **SQL still gates every DE loop.** SQL appears in 79.4% of DE job postings; ~70% of technical SQL rounds at major firms include a window-function question; the single most-cited task is windowed dedup with ROW_NUMBER and a composite tiebreaker. Speed is the separator: candidates who finish that class of problem in 12-15 minutes while narrating get hired. SQL must be the largest section, tuned to the exact canonical patterns.

2. **DE Python is pipeline-shaped, not LeetCode.** Only ~4% of reported DE Python rounds resembled algorithm puzzles. What is asked: parse malformed CSV/JSON, dedup by composite key, sessionization by 30-minute gaps, flatten nested JSON, file I/O, datetime parsing. All of it is Pyodide-native.

3. **Data modeling is the most under-served, most-interviewed skill.** 89% of practitioners report modeling pain; only 5% use semantic models; Kimball (27.8% adoption) is the junior interview canon. "Design a star schema for ride-sharing" is a stock question, "state the grain before drawing tables" is a named strong-candidate signal, and Zach Wilson's bootcamp spends its first two weeks on modeling. This deserves its own early section.

4. **Intern-level cloud questions are conceptual, never console-clicking**, which is exactly what a browser-simulated platform can teach with full fidelity. Service frequency in AWS-flavored loops: S3 100%, Glue 84%, Redshift 76%, Kinesis 67%, Lambda 62%, Athena 61%. The DEA-C01 exam's domain weights (Ingestion/Transformation 34%, Data Store Management 26%, Operations/Support 22%, Security/Governance 18%) are the credible organizing spine.

5. **"Convert to Parquet and partition it" is simultaneously the most repeated correct exam answer and the top real-world cost optimization.** Columnar fundamentals (row groups, footer min/max stats, predicate pushdown, partition pruning, the small-files problem, Athena's $5/TB-scanned model) are the highest-ROI systems topic for juniors and map perfectly onto graded simulated-metadata SQL — and (new, verified) can now be taught on **real Parquet files inspected in-browser** on the platform's pinned runtime.

6. **Idempotency is the spine of the pipelines section.** Every 2025-2026 source converges on three implementations (delete+insert partition replacement, merge/upsert, append+dedup-at-read) and one canonical interview sentence: "at-least-once delivery + idempotent sink = effectively exactly-once." It is gradable literally: run the learner's function twice, assert the state equals one run.

7. **AI-era DE is classic DE with new physics, and fundamentals ARE the AI-era skills.** RAG indexing (parse → chunk → embed → store) is ETL; curation is hashing/dedup/filtering; the biggest text-to-SQL accuracy lever is a semantic model (90.0% → 98.2% for Claude Sonnet 4.6 in dbt's April 2026 benchmark), authored by data engineers. Codegen is commoditizing; modeling, quality, cost governance, and review judgment are appreciating.

8. **AI content is NOT yet in mainstream intern loops.** A 2,817-report interview corpus contains zero RAG/LLM/vector-DB questions in standard DE loops, while AI-native startups and 2026 JDs (e.g. Rivian "Data Engineering Intern, AI & Analytics") increasingly demand it. Teach it as an honestly framed forward-looking differentiator section, not interview-core.

9. **Simulated cloud state is accepted as "hands-on."** DataCamp runs 98 graded boto3 exercises against a mocked S3 backend; LocalStack's engineering lesson is that CRUD-level observable state is sufficient realism; AWS's own SimuLearn wraps labs in stakeholder scenarios with fading guidance. The design risk is not simulation, it is permanent hand-holding (DataCamp's #1 complaint); every module must fade scaffolding to an unscaffolded goal-state-graded exercise.

10. **Concepts outlive tools, and 2025-2026 churn is severe.** Zoomcamp swapped Airflow for Kestra in one year; Kafka 4.0 (March 2025) removed ZooKeeper entirely; Airflow 3.0 killed `execution_date`; dbt is being rebuilt in Rust after the Fivetran merger. Teach generic interfaces (an "orchestrator runs" table, not Airflow-specific columns), name vendors in prose callouts, and explicitly flag which pre-2025 tutorial content is now wrong.

11. **Spark deserves a module, not a line.** Spark appears in 38.7-41.1% of DE postings (the dominant processing framework, ~2.5x Kafka) and in the junior loops of Amazon ("optimize a slow Spark job on EMR"), Databricks, and TikTok — but juniors are tested on conceptual literacy plus metric-based diagnosis, never live cluster coding. Databricks' own Spark UI Simulator (30+ pre-recorded experiments, no cluster) proves the exact cluster-free pedagogy the platform already uses; a 7-9 lesson module of simulated-Spark-UI SQL diagnosis plus a Pyodide "MiniSpark" fills a real sequencing gap (the existing 10GB-shuffle heuristic and EMR framing presuppose shuffle literacy the learner never builds).

12. **The Azure-vs-AWS contradiction dissolves once the citation is updated — but Azure still earns a real module.** The 2026 edition of the same 365 Data Science report flips the stale 2025 stat: AWS 40.3% vs Azure 34.3% vs GCP 12.3% of US DE postings (the report itself flags Azure's 75%→34% drop). An AWS-anchored spine is now evidence-consistent, but a ~34% enterprise-heavy segment (healthcare, finance, insurance, manufacturing — the Midwest/Michigan employer base) warrants dual-labeled concept exercises plus one real Azure/Microsoft-stack module. DP-203 retired March 31, 2025 with no transition path; DP-700 (Fabric) is Microsoft's only DE cert and the parallel anchor to DEA-C01.

13. **pandas is ~20% of DE Python interview questions and the take-home default, and pandas 3.0 (Jan 21, 2026) rewrote the semantics.** Copy-on-Write is now the only mode (chained assignment is dead; `.loc` is the only correct write), `str` is the default dtype, and nanosecond datetimes are gone — a decade of tutorials is now wrong, making 3.0-currency a cheap differentiator. Verified in-browser: real multi-row-group Parquet files can be written and inspected on the pinned Pyodide 0.26.4 (fastparquet + DuckDB `parquet_metadata()`), or via PyArrow on 0.27.7 — never 0.28.x, which dropped pyarrow/polars/duckdb. Polars is real (67.9M monthly downloads, ~9% of pandas) but its wasm build is crippled; teach it as a 1-3 lesson conceptual layer.

## 2. The Modern DE Landscape (2025-2026)

### 2.1 ELT won; the vocabulary expanded
ELT (load raw, transform in-warehouse with SQL/dbt) is the default cloud pattern; ETL persists in regulated/mask-before-landing contexts and legacy systems. Junior interview vocabulary now also includes **Reverse ETL** (pushing curated warehouse data back into CRMs/ad platforms) and **Zero-ETL** (managed replication, e.g. Aurora-to-Redshift). Interviewers reward per-domain tradeoff reasoning ("hybrid" is the honest answer) over dogma.

### 2.2 Warehouse, lakehouse, and table formats
- Deployment reality (2026 State of Data Engineering Survey, n=1,101): **43.8% cloud warehouse, 26.8% lakehouse, 11.7% hybrid**. The warehouse still dominates entry-level jobs; lakehouse literacy is expected. Joe Reis predicts category convergence by 2027.
- **Apache Iceberg is the de facto open-lakehouse standard**: vendor-neutral governance, hidden partitioning + partition evolution, field-ID schema evolution, time travel, broadest engine support (Spark, Flink, Trino, Snowflake, BigQuery, DuckDB, AWS S3 Tables). Iceberg v3 spec ratified mid-2025 (deletion vectors, variant type, geospatial); v4 in design. Delta Lake stays strong inside Databricks (Delta 4.0; UniForm emits Iceberg-readable metadata; a Delta 5.0 proposal would adopt the Iceberg v4 metadata tree). Hudi 1.0 holds the streaming-CDC niche; Paimon and DuckLake (metadata in a SQL DB; 1.0 in 2026) are newcomers. "Consumption gravity": every non-Iceberg format now builds Iceberg-readable surfaces; the reverse investment does not exist.
- **What a junior must know is the problem, not the spec**: ACID transactions, schema evolution, and time travel over Parquet files in object storage, plus "the catalog tells engines which files are current." Catalog wars (Polaris vs Unity vs REST) and spec internals are senior-awareness only.

### 2.3 Parquet and columnar fundamentals
Concretely examinable: files split into **row groups (typically 64-512 MB)** → column chunks → pages, with **per-row-group min/max statistics in the footer** enabling predicate pushdown/data skipping; columnar layout gives high compression and column pruning. Interview staples: columnar vs row for analytics, why CSV is bad (no types, no stats, no splittable compression), what date-partitioning a directory buys, when row-oriented OLTP still wins. Encoding internals (RLE/dictionary details, row-group tuning) are senior.

### 2.4 Data modeling's comeback
- **Kimball dimensional modeling is the junior canon**: facts vs dimensions, star schema, declaring the grain, SCD Types 1/2 (Type 2 dominates), transaction vs snapshot facts, additive vs semi-additive measures, surrogate vs natural keys. Actual adoption: mixed 36.8%, Kimball 27.8%, ad-hoc 17.4%, semantic 5.4%, One Big Table 3.8%, Data Vault 3.3%.
- **Kimball vs One Big Table is a teachable judgment call**, not a war: Zach Wilson's heuristic is Kimball until JOINs exceed ~10GB per side (shuffle cost can be 10-100x), then OBT with nested ARRAY<STRUCT>; OBT trades storage and constraint discipline for zero-shuffle reads. Data Vault 2.0 (hubs/links/satellites) is senior/consultancy awareness at 3.3% adoption.

### 2.5 Medallion architecture: vocabulary yes, dogma no
Bronze (raw, immutable) / Silver (cleaned, conformed) / Gold (business-ready marts) is universal JD vocabulary. The 2025-2026 practitioner critique juniors should be able to echo: three layers applied reflexively to every dataset is an anti-pattern (cost + latency for nothing); silver/gold boundaries are famously ambiguous and must be documented; KPIs built in Silver cause semantic sprawl.

### 2.6 dbt: the ground moved hard, the workflow did not
Timeline (tutorials will be stale on this): dbt Labs acquired SDF Labs (Jan 2025) → **dbt Fusion engine** (Rust, ~30x faster parsing, column-level lineage) beta May 2025 → **dbt 2.0 alpha (June 2026)** rebuilds Core on Rust under Apache 2.0; Core v1.12 is the final Python version. The **Fivetran + dbt Labs merger closed June 1, 2026** (~$600M combined ARR); dbt also contributed SQLMesh to the Linux Foundation; metered features raise open-core concerns.
**What is stable and teachable regardless**: the analytics-engineering workflow. Models as SELECTs, `ref()` builds the DAG, sources, the four generic tests (unique / not_null / accepted_values / relationships), incremental models, docs/lineage. That workflow is what "dbt experience" means in junior postings, and dbt's test semantics ("a test is a query returning violating rows; it passes at zero rows") map one-to-one onto the platform's sql.js expected-set harness.

### 2.7 DuckDB and in-process analytics
~25M monthly PyPI downloads; Stack Overflow usage 1.4% (2024) → 3.3% (2025); v1.4 is LTS. It legitimized scale-up single-node analytics against reflexive Spark, and MotherDuck/DuckLake extend it to cloud/lakehouse. **Direct platform note: DuckDB ships an official WASM build, the one real OLAP engine that could run inside the browser-only constraint**; evaluate it as a future engine alongside sql.js. (See also §6.6: DuckDB 1.0.0 is already bundled in the platform's pinned Pyodide 0.26.4 and verified working against real Parquet files.)

### 2.8 Semantic layers, data contracts, and the "trust for AI" story
**Open Semantic Interchange (OSI)**: Snowflake-led, announced Sept 2025 with Salesforce/dbt Labs/BlackRock/Databricks/Microsoft; Apache-2.0 YAML spec for metrics/dimensions/relationships; v1.0 published Jan 27, 2026. The pitch everywhere: the semantic layer is the trust layer for AI analytics, because NL2SQL agents are fluent but wrong without governed metric definitions. **Data contracts** (producer-side schema + quality + SLA guarantees) are gaining adoption on the back of AI data-quality requirements (Gartner: 70% of orgs adopting modern DQ solutions by 2027). Junior level: know what a contract contains and write SQL quality checks; implementing contract platforms is senior.

### 2.9 Market reality (warehouses, orchestrators, jobs)
- Warehouses: Snowflake most-used; Databricks fastest-growing (~+0.5pp/month, AI-native narrative); Redshift ~30% of AWS-native provisioned deployments; BigQuery leads serverless/event analytics; Microsoft Fabric (Delta-powered) rounds it out. DBMS market $119.7B (2024) → projected $161B (2026), 64% cloud.
- Orchestration: Airflow dominates (24.4% cloud-managed + 22.9% self-managed); **20.5% of teams have no orchestration at all**; Dagster 6.2% (11% in <50-person startups); Prefect 1.3%.
- Jobs — **citation corrected (2026-08)**: the 2026 edition of the 365 Data Science report (published Apr 23, 2026; 943 US Glassdoor DE postings) shows **AWS 40.3%, Azure 34.3%, GCP 12.3%**, alongside SQL 69%, Python 70%, Spark 38.7%, Snowflake 29.2%, Kafka 24.4%, Databricks 16.8%, Airflow 15.8%. The widely quoted "Azure 74.5% vs AWS 49.5%" figure comes from the **superseded 2025 edition** of the same report; the 2026 edition itself flags the swing ("Last year, Azure appeared in 75% of job postings, but this has dropped to just 34% in 2026"). Caveats stated honestly: this is a small single-source US sample, and a 75→34-point one-year swing likely includes methodology drift; the safe claim is *AWS and Azure roughly comparable in US DE postings, AWS ahead*. Corroborating direction: UK ITJobsWatch shows Azure Data Factory permanent postings declining three years running (491 → 386 → 337), even as median ADF salary rose 11.5% to £72.5k — a shrinking-but-senior market. Broader figures hold: SQL and Python remain the spine across editions (79.4%/73.7% in the larger 2025 sample); average DE salary $153K; entry $91K-$155K; ~20,000 net new DE positions added in 2025; **entry-level (0-2 yrs) postings are only ~2% of the market**, which raises the stakes on standing out. The role is drifting from "pipeline developer" toward "platform architect" (distributed systems + cost + AI infrastructure + governance), but core requirements have NOT been transformed by AI: SQL/Python/cloud/ETL remain the spine.

## 3. AWS and the Cloud Section

### 3.1 DEA-C01 as syllabus anchor
AWS Certified Data Engineer - Associate (DEA-C01): **Domain 1 Ingestion & Transformation 34%, Domain 2 Data Store Management 26%, Domain 3 Operations & Support 22%, Domain 4 Security & Governance 18%.** 65 questions (50 scored), 130 minutes, pass 720/1000, compensatory scoring, $150. Explicitly out of scope: ML training/inference, language syntax, business conclusions. In-scope services notably include S3 Tables, MSK, Managed Flink, MWAA, DMS, Lake Formation, Macie, KMS, Cost Explorer. Still current as of July 2026 (no C02).

**Conflict resolution (cert positioning):** AWS recommends 2-3 years experience, and prep sources agree the cert "can help unlock interviews" but is not required and never substitutes for hands-on evidence. Resolution: use the DEA-C01 domain weights and task statements as the cloud section's organizing spine and credibility signal ("this section doubles as DEA-C01 prep"), while positioning the cert honestly as an optional early-career resume differentiator.

Community exam-prep consensus worth designing around: "convert to Parquet and partition" is the single most repeated correct answer; "cheapest / least operational overhead" phrasing almost always points at serverless (Glue/Athena/Firehose/Step Functions).

### 3.2 S3 (100% of AWS loops)
- Flat key namespace; "folders" are prefix conventions; 3,500 writes / 5,500 reads per second **per prefix**.
- **Hive-style partitioning** (`s3://lake/events/dt=2026-08-01/region=us/part-0001.parquet`): crawlers auto-detect `key=value` segments; engines prune by matching predicates against paths; a single `dt=YYYY-MM-DD` key beats nested year/month/day for partition-count sanity.
- **Storage classes + lifecycle** (exam Domain 2.3 verbatim): Standard = hot; Intelligent-Tiering = unknown access ($0.0025/1,000-object monitoring fee, bad for millions of tiny objects); Standard-IA/One Zone-IA = rare but instant; Glacier Instant = ~quarterly; Glacier Flexible/Deep Archive = compliance (minutes-hours restore); Express One Zone = ultra-low-latency. Lifecycle rules transition (e.g. Standard→IA at 30 days, Glacier at 365) and expire.
- **S3 Tables** (GA Dec 2024): fully managed Iceberg "table buckets" with automatic compaction/snapshot expiry; AWS claims up to 3x query throughput vs self-managed. Operational rule: "one catalog, many engines"; two engines writing via different catalogs corrupts the table. Teach raw-files + Hive partitions as the foundation, Iceberg/S3 Tables as the 2025-2026 direction of travel (2-3 forward-looking lessons: ACID, MERGE INTO, time travel, automatic compaction).

### 3.3 Glue (84% of AWS loops)
- **Data Catalog**: Hive-metastore-compatible central metadata shared by Athena/Spectrum/EMR/Glue ETL; first 1M objects/month free; partition indexes speed GetPartitions.
- **Crawlers**: infer schema and partition keys from an S3 prefix. The classic junior debugging story: the crawler guessed a type wrong (everything is `string`) or created one table per partition from an inconsistent layout. This is a purpose-built graded exercise.
- **ETL jobs**: serverless Spark (or Python shell), billed at **$0.44/DPU-hour** (4 vCPU/16GB, 1-minute minimum); job bookmarks give incremental processing; Glue Data Quality evaluates DQDL rules (completeness, uniqueness, freshness).
- **Glue vs EMR vs EMR Serverless** framing: "EMR is Hadoop with ecosystems; Glue is Spark ETL with a Hive metastore"; EMR wins at sustained scale with cluster management; EMR Serverless for ad-hoc petabyte batches. (These lessons presuppose shuffle literacy — see §5.8 for the Spark module that must precede them.)

### 3.4 Athena (61% of loops) and the cost model
- Serverless Trino SQL over S3 via the Glue catalog. **$5.00/TB scanned, 10 MB minimum.** You pay bytes scanned, not rows returned: `count(*)` on raw CSV scans everything; on partitioned Parquet, almost nothing. Documented story: one team's Athena spend doubled in a quarter, 70% of it repeated scans of the same data.
- **Partition projection**: table properties compute partitions in memory, skipping GetPartitions. Gotchas that make great exercises: out-of-range queries silently return zero rows; `SHOW PARTITIONS` doesn't list projected partitions; registered catalog metadata is ignored; projection applies only via Athena.
- **CTAS** is the standard "raw CSV → partitioned Parquet" move (one cited example: ~96.7% cost reduction). Snappy is the usual compression balance; target file sizes 128 MB-1 GB (the small-files problem inflates both S3 request cost and query time). Workgroup bytes-scanned limits are the built-in cost brake. `approx_distinct()` (~2.3% error) vs exact COUNT(DISTINCT) is a standard perf question. Athena also does Iceberg DML (MERGE INTO, time travel).

### 3.5 Redshift (76% of loops)
Sort/dist key reasoning is the archetypal question: DISTSTYLE KEY/ALL/EVEN/AUTO, SORTKEY, skew detection, COPY from S3 (parallel, role-based), UNLOAD, Spectrum external tables for the hot-in-Redshift/cold-in-S3 tiering pattern, Serverless (RPU-hour, auto-scaling) vs provisioned (10-30% faster when well-tuned) tradeoffs, Redshift Data API as the Lambda/Step Functions access path.

### 3.6 Streaming services: a decision plus arithmetic
- **Kinesis Data Streams** (67%): shard = 1 MB/s or 1,000 records/s in, 2 MB/s out; provisioned (shard math) vs on-demand; retention to 365 days; replay; you write consumers.
- **Firehose**: zero-admin delivery, buffers by size/time (~60s min), writes to S3/Redshift/OpenSearch/Snowflake and (2025) Iceberg/S3 Tables; optional inline Lambda transform and dynamic Hive-style partitioning; no replay.
- The discriminator: custom consumers/ordering/replay/sub-second → Streams; "just land it in S3 as Parquet" → Firehose; the team speaks Kafka → MSK (47%).

### 3.7 Lambda (62%), Step Functions, IAM, cost gotchas
- **Lambda**: S3 event notifications deliver `Records[]` JSON (bucket, URL-encoded key, size, event type); hard limits juniors hit: 15-minute timeout, 10 GB memory; async retries twice then drops without a DLQ; the classic footgun is the **recursive trigger loop** (writing output into the triggering prefix). All Pyodide-perfect.
- **Step Functions**: ASL JSON state machines sequencing Lambda/Glue (`.sync` integrations) with retry/catch; Standard vs Express; canonical serverless ETL pattern: S3 upload → EventBridge → Step Functions → Glue crawl + transform → catalog update → SNS. Compare once against MWAA and EventBridge.
- **IAM**: roles with trust policies (nobody embeds keys); explicit deny wins. The canonical Athena "Access Denied" is a missing write permission on the **query results bucket**. Lake Formation layers column/row/cell grants over coarse IAM. Secrets Manager (rotation) vs Parameter Store (static) is a standard exam pairing.
- **Cost gotchas cluster** (all sourced 2025-2026): bytes-scanned billing on unpartitioned CSV; small files; repeated dashboard scans; Glue DPU minimums and always-on interactive sessions ("$0.66 test job" → "$8,500/month"); catalog partition-metadata reads past the free tier; Intelligent-Tiering per-object fees; idle provisioned shards; runaway Serverless RPUs; recursive Lambda loops; no workgroup limits as the meta-failure.

### 3.8 Cross-cloud transferability (mention in every module; Azure now gets more — see 3.9)
Athena ≈ BigQuery ≈ Fabric SQL endpoint; Redshift ≈ BigQuery/Synapse dedicated/Fabric Warehouse; Glue ≈ Dataproc/Dataflow + Data Catalog ≈ ADF; Kinesis ≈ Pub/Sub ≈ Event Hubs; S3 ≈ GCS ≈ ADLS Gen2/OneLake; Step Functions/MWAA ≈ Cloud Composer ≈ ADF pipelines. Flag that Microsoft steers new customers from Synapse to Fabric. Concepts (columnar formats, partition pruning, pay-per-scan, managed table formats) transfer 1:1; close each module with a one-screen mapping. **Update (2026-08): for GCP a one-screen mapping remains sufficient (12.3% of postings); for Azure it is not — the ~34% Azure segment gets dual-labeled exercises plus a real module, per 3.9.**

### 3.9 Azure and Microsoft Fabric: the second cloud (gap-fill, 2026-08)

**Demand reconciliation.** As corrected in §2.9, the 2026 evidence no longer supports Azure-majority demand: AWS 40.3% vs Azure 34.3% vs GCP 12.3% of US DE postings. The AWS-anchored spine is defensible; an AWS-**only** spine still leaves a ~34% segment unserved. The segments split cleanly: AWS skews startups and data-driven tech (DE salary $115k-145k, broadest global role range, ~32% infra share); **Azure skews large enterprises in healthcare, finance/banking, insurance, manufacturing, and public sector** (DE salary $110k-135k) — i.e., exactly the Midwest/Michigan-adjacent employer base (auto OEMs and suppliers, health systems, regional banks/insurers) the platform's target students are likely to interview with. The AWS-vs-Azure question is audience-weighted, not national-average.

**What Azure junior loops actually test** (converged across DataCamp's 37-question Apr-2025 guide, InterviewBit's top-50 ADF, ProjectPro's 50+, K21 Academy, and 2025-2026 walkthrough series):
- **ADF core vocabulary**: pipeline / activity / dataset / linked service / integration runtime / trigger; control flow (ForEach, If, Lookup) vs data flow transformations (Join, Conditional Split).
- **Signature scenario #1 — watermark incremental load**: watermark column + control table storing the last-loaded value + filtered source query + upsert for changed rows. The single most-repeated ADF interview scenario across every source — and conceptually identical to Glue job bookmarks and the course's existing high-water-mark arc (§5.4).
- **Signature scenario #2 — metadata-driven pipelines**: a config table of source/target table names; Lookup fetches it, ForEach loops it, a parameterized Copy activity executes ("copy 200 tables without 200 pipelines").
- Storage choice (Blob vs ADLS Gen2 hierarchical namespace vs SQL DB); batch vs streaming ingestion; ETL vs ELT; Synapse distribution/partitioning/indexing (fading as Synapse folds into Fabric); security (RBAC, encryption, masking).
- **A large share of "Azure DE" interviewing is really Azure Databricks/Spark interviewing** — covered by the cloud-neutral Spark module (§5.8) and lakehouse content, which both tracks inherit.

Critical observation: every one of these is a *concept* question with an Azure service name attached; the identical concepts appear in AWS loops under different names. Junior loops on both clouds are concept-and-scenario interviews, not console interviews — which validates (not changes) the simulated-metadata pedagogy, and makes the device naturally cloud-agnostic: an object-store listing table is S3 *and* ADLS Gen2; a pipeline-run metadata table is Glue *and* ADF; an event-stream table is Kinesis *and* Eventstreams.

**Certifications: DP-203 is dead; DP-700 is the anchor.** DP-203 (Azure Data Engineer Associate) **retired March 31, 2025 with no transition path** — any content referencing it is instantly dated. Its replacement, **DP-700: Implementing Data Engineering Solutions Using Microsoft Fabric** (skills list current as of July 21, 2026), has three equally weighted domains (30-35% each): (1) implement/manage an analytics solution (workspace settings incl. Spark, OneLake, and notably Apache Airflow; deployment pipelines; workspace/item/row/column-level security, dynamic data masking; orchestration, incl. the exam-signature judgment call "**choose between Dataflow Gen2, a pipeline, and a notebook**"); (2) ingest and transform (full vs incremental loads, dimensional-model prep, streaming patterns, OneLake shortcuts, mirroring, PySpark/SQL/KQL transforms, duplicate/missing/late-arriving data, Eventstreams, windowing functions); (3) monitor and optimize (error triage, Lakehouse/warehouse/Spark/query optimization). 100 minutes, 700/1000 pass, open-book Microsoft Learn split screen. It overlaps DEA-C01 heavily at the concept layer; its distinctive additions are KQL/Real-Time Intelligence and Fabric-isms.

**Fabric adoption is enterprise-real but the jobs are senior.** Microsoft claims 70% of the Fortune 500 as paying Fabric customers (mid-2026; ~21k Dec 2025 → 31k+ June 2026), but Fabric-titled DE postings typically ask 3-5 years experience, and no evidence surfaced of intern loops testing Fabric specifics. Fabric is the **forward anchor**; **ADF + ADLS Gen2 + Azure Databricks remain the current Azure junior-loop reality**. Do not teach KQL hands-on (no browser runtime, near-zero intern-loop frequency); mention it in the orientation lesson.

**Verdict**: keep the AWS/DEA-C01 spine; dual-label the concept exercises both clouds test identically; add one real Azure/Microsoft-stack module (~6-10 lessons: ADF vocabulary, the two signature scenarios as graded SQL on simulated control/metadata tables, storage choice, a "Microsoft data stack in 2026" orientation with the DP-700 arc); keep all Azure content at vocabulary/concept level to control staleness (the DP-700 skills list was revised as recently as July 21, 2026).

## 4. AI-Era Data Engineering

### 4.1 RAG pipelines are standard DE work
Canonical 2026 architecture: **offline indexing** (ingest → parse → chunk → embed → store) plus **online querying** (embed query → ANN search → rerank → generate). This is classic ETL with new physics, and it is DE-owned.
- **Parsing tools** (name-drop level): LlamaParse, Unstructured.io (best at tables), Docling, LLMWhisperer; preserve layout, tables, and metadata for filtering.
- **Chunking is contested and therefore great teaching material**: baseline is fixed 500-1,000 tokens with ~200-token overlap; recursive splitting is the workhorse. A Feb 2026 benchmark of 7 strategies found **recursive 512-token splitting beat semantic chunking 69% vs 54%** (semantic fragments averaged 43 tokens): the fancy method loses, so students learn to benchmark, not follow fashion. Advanced: contextual retrieval (Anthropic; prepend an LLM-generated 50-100-token context per chunk, ~69% retrieval-error reduction, one extra LLM call per chunk) and late chunking (embed whole doc, split token embeddings; with it, fixed vs semantic barely differ per arXiv 2504.19754).
- **Vector stores, the pgvector-first consensus**: start with pgvector, move only if you outgrow it. Under ~5M vectors, pgvector returns 5-20ms at 95%+ recall; inflection ~5-10M. Costs at 50M vectors (Timescale benchmark): self-hosted Postgres ~$835/mo vs Pinecone $3,241-$3,889 (75-79% savings). Tradeoffs beyond price: pgvector gives transactional consistency (atomic doc+embedding writes), SQL WHERE/joins, one system; Pinecone gives auto-scaling to billions, single-digit-ms p50, but eventual consistency, no joins, and a **two-store sync problem with orphaning risk**. OpenSearch is the "already running it for lexical search" option. Rerankers (Cohere 3.5, BGE, Voyage) cost $0.025-0.050/M tokens for 20-30% top-k improvement.
- **Freshness is the silent-failure story**: stale embeddings fail with no alert (documented recall drift 0.92 → 0.74). Three staleness sources: source-document drift, embedding-model drift (upgrading ada-002 → text-embedding-3-large makes stored vectors geometrically incompatible; **partial re-embedding creates a broken mixed-generation index**), and chunk-boundary drift. Fixes DEs own: CDC-triggered selective re-embedding (one team paid $12,000/mo for weekly full-corpus re-embeds before going incremental), versioned embeddings, freshness SLAs per content category, and treating the vector DB as a **rebuildable cache** whose durable assets are the raw corpus and a reproducible pipeline.

### 4.2 Data curation for AI training
NVIDIA's NeMo Curator stage order is the reference architecture and nearly every stage is Pyodide-implementable: extract (WARC → JSONL/Parquet) → unicode fixing + language ID → heuristic filters (word count, boilerplate, n-gram repetition) → **deduplication** (exact hash; fuzzy MinHash+LSH+Jaccard; semantic embedding clusters) → classifier quality filtering → **PII redaction** (regex + NER) → **benchmark decontamination** (n-gram match vs eval sets) → blend/shuffle. Numbers: dedup removes 20-30% of raw web data; Falcon RefinedWeb reduced ~1B pages to 2.8TB clean text. This is the clearest case where classic DE skill directly becomes "AI work."

### 4.3 LLMs as ETL primitives, and the reliability engineering around them
Real production uses: classification (Shopify: 30M product classifications/day at 85% accuracy), row-level enrichment (MotherDuck's `prompt()` inside dbt models), entity resolution, unstructured→structured extraction. The new reliability canon:
- **Idempotency is not optional**: a $50 batch job retrying 3x costs $200; retry storms are 30-60% of unexpected monthly inference spend; idempotency keys scoped to the logical unit of work.
- **Batch vs sync economics**: batch inference is 5-10x cheaper per token (up to 30x vs sync API); jobs must resume mid-batch.
- **Dead-letter separation**: non-retryable (content policy, malformed input) vs transient (rate limit, timeout).
- **Circuit breakers on cost**: one documented incident escalated $127/week to $47K/week.
- **Output validation**: structured outputs + Pydantic-style validation with error feedback (Instructor, 3M+ monthly downloads); pin model versions like dependencies.

### 4.4 Text-to-SQL: the model matters less than the context
- dbt Labs (Apr 2026): semantic-layer grounding lifts Claude Sonnet 4.6 from 90.0% → 98.2% and GPT-5.3-Codex from 84.1% → 100%; raw text-to-SQL improved only 32.7% (2023) → 64.5% (2026).
- Spider 2.0 (ICLR 2025): an o1-preview agent scored 91.2% on academic benchmarks but **21.3% on enterprise-realistic workflows**.
- Omni (Apr 2026): **81.2% of text-to-SQL failures are schema/semantic, not syntax**: "correct syntax, wrong meaning," plus "metric drift" (same question, different revenue numbers).
- Snowflake: adding a semantic model lifted Cortex Analyst 57% → 78% on BIRD-SQL. What the DE authors: a YAML semantic model (logical tables, dimensions, facts, metrics, predefined join paths, verified queries).
- Tool landscape (dated name-drops, not labs): dbt Copilot GA March 2025; Databricks Assistant/Genie Code + Lakeflow spring 2026 (a cited benchmark: coding-agent success 32.1% → 77.1% with Genie Code); vendor posts acknowledging no limitations is itself a teachable point.

### 4.5 Agents, feature stores, context engineering
- **Agentic reality check**: only ~5.2% of orgs run AI agents in production; 72% want AI-assisted coding but only 24% trust it to manage pipelines. What trust requires: reasoning traces, auditable logs, human-in-the-loop checkpoints, eval harnesses. More engineering rigor, not less.
- **Feature stores** survived the LLM wave (Feast, Tecton, Hopsworks, cloud-native): core junior concepts are the offline/online split, point-in-time-correct training joins (label leakage), and training/serving skew. "Operationalize feature stores" now appears in DE job requirements.
- **Context engineering**: as SQL generation commoditizes, the governed context (semantic layer + ontology + lineage + access policy + active metadata) becomes the durable asset. Gartner: 60% of agentic analytics projects relying on MCP alone without a semantic layer will fail by 2028. Atlan/Snowflake: context-enriched metadata improved SQL-generation accuracy 3x over schema-only prompts. OpenAI's internal data agent went 22+ minutes → 1m22s per question once the context/memory stack was in place; the delta came from context, not the model.

### 4.6 Conflict resolution: how much AI-era content, and where
The ai-era lens shows RAG entering interview banks (DataCamp's 30-question set, JD language); the interview lens shows zero AI content in 2,817 mainstream DE loop reports. Both are true, and the ai-era lens itself concedes fundamentals still gate (SQL 79.4%, Python 73.7% of postings). **Resolution: a full AI-era section positioned explicitly as a forward-looking differentiator ("2026 JDs demand it; most intern loops don't test it yet; AI-native startups do"), placed after the interview-core sections, framed throughout with the commodity-vs-valuable narrative so it reinforces rather than displaces fundamentals.** Interviewer expectation where it IS asked: name specific parameters (chunk sizes, model versions, reranker choices, recall numbers), not vocabulary; model answers must model that specificity.

## 5. Pipelines, Orchestration, Streaming, Reliability

### 5.1 Orchestrators: Airflow is the vocabulary, assets are the idea
Airflow is the hiring-pool default (30M+ monthly downloads, 80,000+ orgs, State of Airflow 2026: 5,800+ respondents, 89% expect revenue-workload use, dbt its most-paired tool at 44%). **Airflow 3.0 (GA April 2025) changed what juniors should learn**: `execution_date` is gone (think **logical date + data interval**: the run is responsible for a time range, not "when it ran"); backfills are scheduler-managed and first-class; event-driven scheduling and **Assets** converge on Dagster's asset-centric model. Dagster wins greenfield dbt-heavy teams; Prefect is the small-team Python-decorator option. Teach Airflow concepts as lingua franca, the asset-oriented idea in exactly one lesson, and no hands-on Dagster/Prefect.

**Conflict resolution (orchestration depth):** the interview lens says Airflow appears as conceptual DAG questions, almost never code; the pipelines lens justifies a full section. Resolution: a full pipelines/orchestration section, but graded through **generic simulated metadata** (`pipeline_runs`/`task_instances` tables) and Python reliability exercises rather than Airflow-specific coding, because the underlying reasoning (idempotency, backfills, freshness SLAs, retries) IS tested in interviews even though Airflow code is not. The same resolution applies to dbt: on every JD, rarely tested; teach the workflow and test semantics hands-on in SQL (they're transferable and map onto the existing harness), skip tool-specific labs, and confine the 2025-2026 corporate upheaval to one callout.

### 5.2 DAG design canon (Astronomer, interview-quotable)
Idempotent runs bound to an immutable data interval; atomic tasks (separate E/T/L, independently re-runnable); **never `datetime.now()` in pipeline logic** (the #1 anti-pattern: breaks reruns/backfills; at top level it executes on every ~30s scheduler parse); retries ≈2 deliberately; `catchup=False` unless designed for it; incremental filtering by timestamp/sequence ID.

### 5.3 Idempotency: the core property
Three implementations, converged on by every source:
1. **DELETE + INSERT** (partition replacement for the run's date). Simplest, works everywhere.
2. **MERGE / UPSERT** on a natural/business key. (sql.js note: SQLite has no MERGE keyword; teach MERGE as concept/model-answer, grade via `INSERT ... ON CONFLICT DO UPDATE` or delete+insert.)
3. **Immutable append + dedup-at-read** (`ROW_NUMBER()` keeps latest per key).
The interviewer-grade sentence: *"True exactly-once is impossible; at-least-once delivery + idempotent sink = effectively exactly-once."* Idempotency is the precondition for retries, backfills, and late-data reconciliation, so it should be the spine of the entire section, graded literally (run the learner's `apply_batch` twice; assert state equals one run).

### 5.4 Incremental loading and CDC
- **The causal chain is the lesson**: high-water mark (`> watermark` filter, ~80% of use cases) → why a safety overlap margin is required (in-flight transactions commit with earlier timestamps) → why overlap creates duplicates → why the sink must be an idempotent merge. (Dual-label note: the control-table watermark pattern is also the single most-repeated **ADF** interview scenario — see §3.9 — so one graded exercise serves both cloud tracks.)
- **CDC**: query-based (poll `updated_at`; simple but **misses deletes** and loads the source) vs log-based (Debezium reading the WAL/binlog; captures everything at near-zero source cost but needs schema discipline). The Debezium envelope is concrete and simulatable: `{op: 'c'|'u'|'d', before, after, ts_ms, source}`; `before` null on insert; deletes carry `before` only. Healthy flow: capture → land raw → dedupe → merge; CDC feeds SCD Type 2 cleanly. "The hardest part of a CDC pipeline is schema evolution" appears verbatim in 2026 question banks.

### 5.5 Backfills, late data, batch-vs-streaming
- Backfillable = accepts a date parameter, no hardcoded "today." Pitfalls: wall-clock leakage, non-deterministic sources, downstream aggregates needing recomputation, unbounded-catchup cost blowups. Common production pattern: a bounded rolling window (last ~3 days) recomputed every run so late arrivals self-heal.
- **Event time vs processing time** is the single most transferable streaming concept; a watermark asserts "all events ≤ t have arrived" and controls the completeness-vs-latency tradeoff. Late-data options: drop, allowed-lateness updates, side-output/DLQ, or append-only + nightly window reprocess. DLQ pattern for poison records: store record + error + timestamp, alert past ~5%, never halt.
- **Batch vs streaming is a decision framework, not a survey**: "what decision consumes this data and what latency does that decision require?" If batch satisfies the requirement, pick batch; micro-batch every few minutes covers most "real-time" asks. Streaming justified: fraud (<seconds), real-time personalization, operational systems. "Defaulting to streaming because it sounds impressive" is a named junior mistake.

### 5.6 Kafka and Flink
- Core vocabulary interns are quizzed on: topic → partitions (unit of parallelism) → offsets (committed offset = next to read) → consumer groups (each partition owned by exactly one group member) → **consumer lag** (log-end minus committed). Partition-key choice and hot-key skew are junior-reachable.
- Delivery semantics via offset-commit ordering (crisp and gradable): commit before processing = at-most-once; commit after = at-least-once (Kafka's default posture); exactly-once needs transactions + `read_committed` (senior awareness). Producer `enable.idempotence` kills resend duplicates; `acks` trades latency vs durability.
- **Kafka 4.0 (March 2025) removed ZooKeeper entirely (KRaft only; controller failover <5s vs 18-30s); KIP-848 rebalances are GA.** Pre-2025 prep material still teaches ZooKeeper; the course must explicitly flag this as outdated.
- Flink is intern-awareness: event-time windows (tumbling/sliding/session), watermarks, allowed lateness, checkpointing for failure recovery; backpressure gets one conceptual lesson; Lambda-vs-Kappa is architecture vocabulary.

### 5.7 Testing and observability
- **dbt test semantics** are perfectly gradable in sql.js: a test compiles to a query returning violating rows and passes at zero rows. Cover the four generic tests plus the dbt 1.8+ **unit test vs data test** distinction (fixture-tested logic in CI vs every-run data checks), now standard interview vocabulary. Ecosystem in prose: Great Expectations at ingestion, Soda for trailing-window anomaly monitoring.
- **Data observability, five pillars** (Monte Carlo framing, industry-standard): freshness, volume, schema, distribution, lineage. Intern-implementable monitors: stale-table vs SLA, day-over-day row-count anomaly (z-score vs trailing 7 days), schema drift from a column catalog, missing partitions. The most-missed production failure: **silent success, pipeline green but zero rows written**; "data downtime" triage is a great free-response scenario.
- **Schema evolution as precise rules**: Schema Registry BACKWARD (default, because you deploy consumers first and can rewind) / FORWARD / FULL / `_TRANSITIVE`; Avro mechanics: add fields with defaults = backward-compatible, delete only fields that had defaults, renames break everything; batch-side equivalents: additive-only columns, versioned tables, schema-on-read formats. Gradable as a Python `is_backward_compatible(old, new)` checker.

### 5.8 Distributed compute: Spark for junior loops (gap-fill, 2026-08)

**Demand justifies a module, not a line.** Spark appears in **38.7-41.1% of DE postings** (365 Data Science, 1,000+ ads analyzed 2025-2026) — the dominant processing framework, ahead of Snowflake (29.2%) and Databricks-as-platform (16.8%), and ~2.5x Kafka. It appears in the loops of the biggest junior-DE hirers: Amazon (explicitly asks "optimize a slow Spark job on EMR" plus Redshift/S3/Spark tradeoffs), Databricks (Spark internals at all levels; their intern SWE loop even probes lazy data structures), and TikTok (shuffle mechanics and partitioning per Blind reports). A curriculum that gives Kafka a module and Spark one line is inverted relative to demand. But juniors are tested on *conceptual literacy + metric-based diagnosis*, never cluster ops or live PySpark coding — so it needs a **7-9 lesson module**, not a full section with a real runtime.

**The junior canon** (converged across DataVidhya's tiered "70 Real Asks (2026)", DataCamp's PySpark Top 36, PipeCode, InterviewBit, Spark Playground):
- **Tier A — every junior must answer (foundational)**: driver vs executor model (driver runs `main()`, builds the plan, schedules tasks; executors hold partitions; one task per vCPU slot); lazy evaluation (transformations build a plan, only actions — `collect`/`count`/`write`/`show` — execute; enables whole-plan optimization); narrow vs wide transformations (wide = shuffle = disk I/O + serialization + network, "the most expensive operation in Spark"); job → stage → task hierarchy (stages cut at shuffle boundaries; 1 partition = 1 task); RDD vs DataFrame (DataFrames get Catalyst + Tungsten); `repartition` vs `coalesce`; `cache()` vs `persist(storageLevel)`; Spark vs MapReduce.
- **Tier B — the junior differentiators (asked constantly, weak candidates fail here)**: **broadcast join** (auto-threshold `spark.sql.autoBroadcastJoinThreshold` = **10MB**, practical manual ceiling ~100MB; converts a wide join to narrow; too-large broadcast → driver OOM; sort-merge for large-large); **skew** (straggler tasks; detection signal cited verbatim across corpora: **max task time vs median task time gap in the Spark UI**; fixes: salting, broadcast the small side, AQE skew-join splitting); **OOM diagnosis fork** (driver OOM = a `collect()` on big data; executor OOM = too-few partitions, too many cores/executor, low `memoryOverhead`); **`spark.sql.shuffle.partitions` default = 200** and why that's wrong for both tiny and huge data (2-4 partitions per core heuristic); **AQE** (coalesces post-shuffle partitions, converts sort-merge→broadcast at runtime, splits skewed joins; on by default since Spark 3.2 / Glue 4.0 — answers omitting AQE read as 2019-era); reading `.explain()` at recognition level (`Exchange` = shuffle = stage boundary); Parquet advantages (pruning, pushdown, min/max skipping).
- **Tier C — senior scope, EXCLUDE**: Tungsten internals, custom partitioners, streaming state/checkpointing/watermarks/backpressure remediation, MLlib, dynamic allocation tuning.

**Currency (2025-2026)**: **Spark 4.0 shipped mid-2025** (GA on EMR): ANSI mode ON by default (divide-by-zero/overflow/bad casts fail fast instead of silently nulling — this changes classic "silent null" gotcha answers), new VARIANT type for semi-structured data, Spark Connect, Java 17 default. One callout lesson-note, not a module. Databricks refreshed its Spark Associate Developer exam guide Sep 2025 (Spark 3.5.x-era; exact domain weightings could not be extracted — do not quote weightings).

**How to teach in-browser (no JVM, no cluster) — strong precedent**: PySpark cannot run in Pyodide (JVM dependency, confirmed), but **Databricks' own Spark UI Simulator** — 30+ experiments of pre-recorded Spark UI captures + config + source, used to teach diagnosis without any cluster — proves the exact pedagogy. Translation: expose a *simulated Spark UI as queryable sql.js tables* (`stages(stage_id, shuffle_read_mb, shuffle_write_mb, num_tasks)`, `tasks(task_id, stage_id, duration_ms, spill_mb, records_read)`, `executors(...)`) and grade diagnosis queries ("return the stage where max(duration)/median(duration) > 5" = skew; "find the stage whose shuffle_write exceeds 10GB" — grounding the Kimball-vs-OBT heuristic the curriculum already uses). For lazy evaluation, a ~100-line pure-Python **"MiniSpark"** teaching class (partitioned lists; `.map/.filter/.groupBy/.join` build a plan; `.collect()` triggers execution; `.explain()` prints stages with `Exchange` markers) runs fine in Pyodide — SQLFrame proves the whole PySpark DataFrame API needs no JVM. Commercial validation: sparkplayground.com monetizes exactly this interview-prep niche with a server-backed compiler; client-side simulation avoids that cost entirely. The free-response engine handles the Amazon ask verbatim: "your EMR job takes 4 hours; the UI shows one 40-minute task vs a 2-minute median — diagnose and fix" → model answer walking skew → salting/broadcast/AQE.

**Sequencing verdict**: the module goes AFTER storage/Parquet/partitioning (shuffle literacy presupposes file-partitioning literacy) and BEFORE Kimball-vs-OBT and the Glue/EMR lessons (which presuppose shuffle knowledge). Frame examples in Glue-on-Spark/EMR terms — AWS's own Glue tuning guide enumerates exactly this concept list — reinforcing the AWS section without adding a Databricks-platform dependency. Numbers to hard-code into lessons and grading: 10MB, ~100MB, 200, 2-4/core, max-vs-median ratio, AQE default-on since Spark 3.2/Glue 4.0.

Pipeline-shaped, explicitly not LeetCode (~4% algorithmic): parse malformed CSV / gzipped JSON lines; dedup events keeping latest per composite key; group-by-key in O(n); inner-join two lists of dicts without a database; flatten nested JSON to dot-paths; sessionization by 30-min gaps; top-N with deliberate tie handling; file I/O and datetime parsing (the Amazon staples); memory-awareness as concept ("stream a 50GB gzipped JSONL on an 8GB machine"). A predictable ~20% slice of Python DE questions is pandas/DataFrame material — see §6.6.

### 6.5 Modeling, pipeline design, cloud, take-homes, behavioral
- **Modeling**: "the most underprepped skill." Intern level = knowledge questions (star vs snowflake, fact/dim, OLAP/OLTP); the probe progression: grain first, SCD 1/2/3 (Type 2 dominates), transaction vs snapshot facts, additive vs semi-additive, surrogate vs natural keys. Example: "ride-share warehouse; driver moves cities" → completed-trip-grain fact + Type 2 dimension.
- **Pipeline design** leaks into other rounds: "design a daily pipeline from Postgres/an API/CSV drops to the warehouse" (expected: orchestrator named, batch-vs-streaming call, idempotency, one failure mode); backfill 2 years without breaking today; where do late events go; CDC vs dual writes. Junior bar = sensible end-to-end flow with correct vocabulary; senior signal = failure modes raised **unprompted**.
- **Cloud**: service frequencies from 156 AWS-flavored loops: S3 100%, Glue 84%, Redshift 76% (sort/dist keys, DS_DIST_BOTH plans), Kinesis 67%, Lambda 62%, Athena 61%, EMR 58%, MSK 47%. Junior questions are tactical (partitioning schemes, "Parquet with Snappy, date-partitioned, Standard→IA→Glacier lifecycle", when-to-use-which); IAM/VPC and cost optimization are L5+ (67% of senior loops). - **Tool reality check**: dbt on every JD but rarely tested; Airflow conceptual only; Spark a tradeoff conversation (except Databricks) — see §5.8 for the concept/diagnosis canon it draws on.
- **Take-homes** have one dominant shape: ingest CSV/JSON/API → transform per business rules → load → answer questions (SpotOn, HelloFresh-style publics). ### 6.6 DataFrame tooling: pandas, Polars, PyArrow (gap-fill, 2026-08)

**How much pandas shows up.** Datavidhya's "50 Python Interview Questions for Data Engineers (2026)": ~10 of 50 are pandas/DataFrame questions, 40 pure Python — pure-stdlib munging remains the majority of the live round (validating the existing spec), but a ~20% pandas slice is standard and predictable. The pandas ten are a near-perfect syllabus: Series vs DataFrame; `.loc` vs `.iloc`; missing/NULL handling; merge + join types; **"How would you read a 100GB CSV file with only 16GB of RAM?"** (the canonical chunking/out-of-core question); pivot tables; string→datetime conversion; `groupby()`; `apply()` vs `transform()`. Real company questions (StrataScratch) — Airbnb `drop_duplicates`/`groupby().min()`, Spotify filter+`sort_values`, Salesforce salary-vs-department-average (`groupby`+`merge`, the pandas twin of a window function), Uber channel effectiveness — are the platform's existing SQL exercises re-expressed in pandas, a cheap authoring win via dual SQL/pandas tracks on the same datasets. Screening-round expectations (Interview Query, Data Engineer Academy): pandas/NumPy plus scenario ETL/debugging prompts, where narrating debugging steps and stating assumptions scores as well as perfect syntax. DataCamp's competing DE-in-Python track is pandas-first. 2026 skills guides now phrase the requirement as "pandas/Polars" — pandas the anchor, Polars riding along.

**Take-homes: pipeline-shaped, pandas-optional but pandas-default.** SpotOn (public repo): Kaggle CSVs → object storage → Postgres → `docker-compose up` → scaling notes; graded on one-command runs, populated tables, honesty about shortcuts. HelloFresh (leaked spec): mock recipes API → **flatten nested JSON** (incl. `nutrition - Energy (kJ)`) → `YYYY_WW_menu.csv` → rank top-10 → S3, wrapped in Airflow + Docker + tests + CI. Norms: ~2-hour intended scope; rubrics reward error handling, idempotency, logging, documentation, and scaling commentary — **pipeline shape, not pandas API trivia**. Nobody grades `.loc` syntax; pandas is just the default solve tool.

**pandas 3.0 landed January 21, 2026 — teach the new semantics.** Copy-on-Write is the default and only mode: chained assignment (`df["foo"][mask] = 100`) no longer works at all, `SettingWithCopyWarning` is gone, and `.loc[mask, "col"] = x` is the only correct write — a decade of tutorial content is now wrong. `str` dtype is default (PyArrow-backed if installed, NumPy-object fallback; PyArrow "strongly recommended" but not required — PDEP-10's hard requirement was walked back). Datetime default resolution is no longer nanoseconds (kills the 1678-2262 Timestamp range trap; ties into the platform's dates/times knowledge component). `pd.col()` expression syntax arrives, explicitly Polars-influenced. 2026 prep content is already minting "what changed in pandas 3.0" questions — knowing CoW is a cheap junior differentiator.

**Polars: real adoption, emerging-but-secondary interview presence.** Downloads (Aug 2026): polars 67.9M/month vs pandas 731.9M/month — ~9% and climbing fast (from ~2-3% in 2024), nowhere near parity. Flagship case study (PyData Global 2025): GitHub migrated a 400GB/night ETL from pandas (128GB machine, 90 min) to Polars (32GB, 11 min), ~75% cost cut. No evidence Polars is *required* live-coding material for intern/junior roles: a talking-point layer, not a syntax layer.

**Browser feasibility — empirically verified against the actual runtime** (Node spikes on official CDN wheels; the platform pins **Pyodide v0.26.4** at `public/workers/python-sandbox-worker.js:36`):

A small in-memory Polars demo module is feasible; Polars-on-Parquet and any performance demo are not.
- **Pyodide 0.28.x removed pyarrow, polars, and duckdb from the distribution** (build issues; confirmed in the 0.28 changelog and a 0.28.3 lock-file check). Pinning decision: **0.26.4 (status quo, DuckDB path) or exactly 0.27.7 (PyArrow path) — never 0.28.x** for these lessons.

**Verdict**: the curriculum needs a pandas module sized at roughly the interview-bank ratio (~8-12 lessons vs ~40 pure-Python), a pandas-based take-home capstone graded on pipeline shape, PyArrow/DuckDB as the *instrument* that turns Parquet lessons from simulated tables into real file inspection, and Polars as a thin conceptual layer (1-3 lessons).

Target **~60-110 total hours** (incumbent range 57-107h). Avoid the documented failure modes: no lab brokering, no fill-in-the-blank-only levels, no stale tool versions, no overselling certificates; sell skill evidence (graded transcripts, knowledge map).

## 9. Curriculum Implications (deduplicated, prioritized)

**Tier 1 — structural decisions**

1. Organize the whole course on the Reis lifecycle spine (source systems → ingestion → storage → transformation/orchestration → serving) with security, ops, and data quality as recurring threads; it is the mental model interviewers and every major course share.
2. Make SQL the largest section and explicitly interview-canon: windowed dedup with composite tiebreakers, gaps-and-islands, 7-day rolling averages, MoM growth, anti-joins three ways, conditional-aggregation pivots, recursive CTEs, JSON functions (all sql.js-supported).
3. Give data modeling its own early section (star schema, grain-first, facts/dims, SCD 1/2, additive measures, Kimball-vs-OBT with the ~10GB-join-side heuristic), using the free-response engine for "design a model for ride-share/e-commerce" with model answers. It is the most-interviewed, least-taught skill.
4. Make the Python section pipeline-shaped, framed as the "T" of ELT: malformed-file parsing, composite-key dedup, sessionization, JSON flattening, file I/O, datetime parsing, top-N with ties. No LeetCode-style algorithms. The pure-stdlib dict/list track stays the larger live-round track, with the pandas module (item 10) alongside it at the observed ratio.
5. Structure the cloud section by DEA-C01 domain weights (34/26/22/18) and prioritize services by measured interview frequency (S3 100%, Glue 84%, Redshift 76%, Kinesis 67%, Lambda 62%, Athena 61%); state that the section doubles as optional DEA-C01 prep while positioning the cert as a resume signal, not a requirement. Keep ML training/inference out of scope, spending that budget on data quality and observability. **Cite the April-2026 cloud-demand data (AWS 40.3% vs Azure 34.3% vs GCP 12.3%, 943 US Glassdoor postings) and never the superseded 74.5%-Azure figure from the 2025 edition** — the AWS-anchored spine is then evidence-consistent, with the honest single-source-sample caveat.
6. Build a full pipelines/orchestration/streaming section with **idempotency as its spine**, taught via the three implementations and graded literally (grader runs the learner's function twice, asserts state equals one run; grader redelivers duplicate messages, asserts final state).
7. Add the AI-era section as an honestly framed forward-looking differentiator (JDs and AI-native startups demand it; mainstream intern loops don't test it yet), placed after interview-core content and threaded with the commodity-vs-valuable numbers (5.2% agents in production, 24% pipeline trust, SQL in 79.4% of postings) to inoculate against "why learn SQL when AI writes it."
8. Give distributed compute a dedicated **Spark module of 7-9 lessons** (not one lesson, not a full section): Spark is in 38.7-41.1% of postings and in Amazon/Databricks/TikTok junior loops, but juniors are tested on concepts and metric diagnosis, never live cluster coding. Sequence it AFTER Parquet/partitioning/object-storage and BEFORE Kimball-vs-OBT and Glue/EMR lessons — the existing 10GB-shuffle heuristic and EMR framing presuppose shuffle literacy the learner currently never builds. Label it interview-prep ("what Amazon/Databricks actually ask").
9. Keep AWS/DEA-C01 as the primary spine but add a **real Azure/Microsoft-stack module of ~6-10 lessons** (not a one-screen mapping note), targeted at the enterprise/finance/healthcare/manufacturing segment that skews Azure and dominates Midwest/Michigan hiring; name **DP-700** as the parallel certification anchor alongside DEA-C01 in course framing, and never reference DP-203 (retired March 31, 2025, no transition path). Keep all Azure content at vocabulary/concept level to control staleness (DP-700 skills revised July 21, 2026; Synapse actively folding into Fabric).
10. Add a **pandas module of ~8-12 lessons** sized to the observed interview ratio (~20% of Python DE questions): Series vs DataFrame, loc/iloc, missing values, groupby/agg, merge + join types (with the row-explosion gotcha), pivot/melt, to_datetime, apply vs transform vs vectorization, drop_duplicates, and the canonical "100GB CSV on 16GB RAM" chunked-reading lesson. Teach **pandas 3.0 semantics from day one** (only `.loc` writes, no chained assignment, Copy-on-Write mental model, str dtype, microsecond datetimes) with one explicit "pandas 3.0 changed this in Jan 2026" differentiator lesson; enable `pd.options.mode.copy_on_write=True` (and `future.infer_string`) in the lesson harness so the Pyodide 2.2/2.3 runtime matches 3.0 behavior. Scope Polars to 1-3 lessons (see item 36).
11. Tag every lesson "know cold" vs "awareness" per the Section 8 table (mirroring the SQL L5 triage pattern) so interns spend practice time on SQL/Python/modeling/pipeline-design, not format wars.
12. Enforce scaffold-fade in every module: guided walkthrough → fill-in-the-blank → from-scratch → unscaffolded "boss" exercise graded only on goal state. This is the direct counter to DataCamp's #1 complaint and copies Cloud Quest's DIY phase.
13. Target ~60-110 total hours and calibrate practice volume to the prep consensus of 50-80 problems (~30 SQL, ~20 Python, ~10 modeling); market both numbers on the course page. Position as "zero-setup, in-browser, graded like an interview, beginner-safe."
