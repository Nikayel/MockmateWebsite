# SD Interactivity Council: judge verdicts (2026-07-23)

Rationale record behind `INTERACTIVITY-PLAN.md`. Three independent judges over the 12-level audit aggregate.

## Learning science

The current Read-then-Design loop is half of a good design. The single free-text design write is genuine generation-effect practice, but it arrives after 600-950 words of unbroken expert prose with zero interim retrieval, so learners hit the write with working memory already saturated and misconceptions intact. Under CLT the problem is not intrinsic load (the material is legitimately hard) but extraneous load (ASCII fences, 150-word enumeration paragraphs, no signaling) and wasted germane-load opportunities (211 lessons have nameable misconceptions and no check ever confronts them). Learning-per-build-hour ranks the interventions decisively: (1) the `check` fence is first by an order of magnitude - one zero-animation build serves 211 lessons and exploits the two best-evidenced effects in the literature (testing effect, pretesting/prediction error); (2) player-level segmenting is second - a player feature, not a widget, that fixes pacing across all ~208 lessons at once; (3) the `sequence` widget with failure toggles is the single highest-value visual build (53 high-value lessons; the curriculum's hardest material in L1/L5/L6/L8 is temporal and currently narrated in prose); (4) one config-driven formula-calc engine (capacity-calc) absorbs availability-calc, burn-rate-sim, tail-latency-explorer, utilization-curve, and fanout-explorer as presets, turning ~20 lessons' arithmetic-as-prose into manipulables for one build; (5) the reusable hands-on sims that serve 3+ lessons or ARE a worst lesson's crux (queue, cache, rate-limiter, hash-ring, quorum-explorer, partition, replication-lag, watermark, shuffle-shard, fanout, geo-grid). Dosing for checks: 3-4 per 1,000 teach words (one per concept chunk of 250-300 words), each targeting a NAMED misconception, placed BEFORE the resolving paragraph so the learner commits a prediction and experiences the correction (pretesting beats post-testing for misconception repair), plus one cumulative check at teach end as a bridge into the design write; feedback must be immediate and explanatory, stakes zero, no gating. Segmenting: yes for every teach over ~500 words, via learner-paced progressive disclosure (heading + continue) rather than splitting into more lessons - splitting would inflate navigation overhead and break the lesson-count/SR contract; accordion treatment for the reference-sheet lessons (template-pitfalls, latency-numbers). Seductive-details discipline matters here because framer-motion makes decoration cheap: cut abr-sim, compression-bits, hash-chain, sharded-counter, board-zones, stream-windows, merkle-diff, and graph-traversal - each animates something the learner can only watch, where the transferable claim fits in one static figure plus a check. Mandatory interaction defaults, encoded in the fence schema so authors cannot skip them: predict before animate (every sim opens with a one-tap prediction prompt); worked-example script plays before free manipulation (worked-example effect for novices); one variable unlocked at a time with staged unlock of the rest; immediate causal read-out tied to exactly one output chart; no autoplay loops; reduced-motion parity; reset button; target ~60-90 seconds of interaction per sim. Net: consolidate the 66 proposed slugs to roughly 22-24 actual builds (8 cut, ~30 merged into shared engines or downgraded to staged-reveal statics), and ship in the order check -> segmenting -> sequence -> calc engine -> sims.

### Recommendations

- [P0] **Build the check fence first and dose it misconception-first**: One new csdiagram-style fence type (JSON in a `check` fence, zod-validated like lib/tutorials/diagrams/schema.ts) serving 211 lessons with zero animation cost. Dosage: 3-4 checks per 1,000 teach words, i.e. one per 250-300-word concept chunk, plus one cumulative check at teach end as the bridge into the design write. Placement: for misconception checks, put the prediction BEFORE the resolving paragraph so the learner commits and experiences the correction (pretesting/prediction-error repair beats post-hoc quizzing); for consolidation checks, after the chunk. Every existing bolded 'Interview nuance' block is a ready-made check: the four formats needed are predict-the-outcome, classify-the-statement, pick-the-best-move, and spot-the-flaw. Feedback must be immediate and explanatory (why the wrong answer is tempting), stakes zero, no gating, retry allowed. Log answer distributions so real misconception rates guide later revision.
- [P0] **Add learner-paced segmenting to SystemDesignLessonPlayer, not as a widget**: Progressive disclosure at the player layer: auto-split any teach over ~500 words on H2/H3 boundaries (or an explicit section marker) into 2-4 learner-advanced sections with a continue affordance, persisting position. This is Mayer's segmenting principle; it fixes pacing across all ~208 lessons without re-authoring content, where a per-lesson widget would not. Use accordion treatment for reference-sheet lessons (sd-l0-template-pitfalls's six lists, sd-l0-latency-numbers's tables) so they read as retrievable cards. Do NOT split lessons into more lessons: that inflates navigation overhead and breaks the lesson-count and spaced-repetition contracts. Keep SableTutor aware of which sections are revealed.
- [P0] **Build the sequence widget with failure toggles and a predict-next-step affordance**: The single highest-value visual build: 53 high-value lessons, and the hardest material in L1/L5/L6/L8 (handshakes, dual-write races, sagas, coordinator crashes, OAuth/PKCE flows) is temporal and currently pure prose. Requirements: learner-stepped (never autoplay), lanes for parties, per-step state annotation, authorable failure toggles (drop message, crash node, timeout), and an optional predict-next-step prompt before revealing a step. Design the fence schema so retry-storm-sim, inventory-race, hol-blocking, and cursor-vs-offset land as authored scenarios of this one widget rather than separate builds.
- [P1] **Consolidate all slider-to-formula slugs into one calc engine**: Build capacity-calc as a config-driven formula engine: fence JSON declares inputs (sliders with ranges), formulas, and outputs (numbers plus one optional chart). Presets then absorb availability-calc (serial ceiling, 1-(1-a)^n), burn-rate-sim (budget depletion timeline), tail-latency-explorer (1-(1-p)^N), utilization-curve (1/(1-rho)), and fanout-explorer arithmetic. One build serves ~20 lessons and converts every arithmetic-as-prose complaint in L0/L4/L7 into a manipulable. Enforce single-variable exploration: sliders unlock one at a time on first use.
- [P1] **Encode load-protecting interaction defaults in the widget schema**: Make the defaults unskippable by putting them in the zod schema rather than the authoring guide: (1) every sim supports and defaults to a predictPrompt shown before the first animation frame runs (predict-before-animate); (2) a script field defines a worked-example run that plays before free manipulation unlocks (worked-example effect for novices); (3) staged variable unlocking so exactly one manipulable is live at a time; (4) immediate feedback tied to one causal read-out, max one chart per sim; (5) no autoplay loops, reset always visible, reduced-motion renders final states as stills, target 60-90 seconds of interaction. Extend docs/csdiagram-authoring.md with these as hard rules and cover them with the existing render-based content-integrity test pattern.
- [P1] **Build the eleven reusable sims in lessons-served order**: After check/segmenting/sequence/calc-engine, build the hands-on sims that serve 3+ lessons or are a flagged-worst lesson's crux, in this order: queue-sim, cache-sim, rate-limiter, hash-ring, quorum-explorer (with acks and BFT presets), partition-sim, replication-lag, watermark-sim (absorbing watermark-window), shuffle-shard-sim, fanout-sim (absorbing fanout-explorer), geo-grid (absorbing geo-cells). ## Engineering

FEASIBLE with the existing house pattern, and no new runtime dependency is warranted. Architecture: (1) TWO fences, ONE shared plumbing layer. Keep ```csdiagram for stateless, replayable visuals and extend its union with the SD static/staged types (topology, ladder, latency-ladder; table and er are reused as-is, zero build). Add ONE new fence ```cswidget for stateful interactives (checks, sequence steppers, hands-on sims). Reasons: (a) different render contract — diagrams are pure functions of spec and safe to render eagerly inline; widgets carry interaction state, reveal semantics, focus management, and an aria-live announcement channel, and want dynamic import as a unit; (b) a 30+ member union in one schema file violates the repo's own file-size rule — two unions split by state semantics keep each cohesive; (c) the plumbing generalizes trivially: parameterize extract.ts by fence label, add one branch in lib/markdown/components.tsx, share DiagramErrorBoundary/DiagramError, and wrap every widget in a new WidgetFrame that owns the a11y shell. (2) Top-4 schemas (zod, all superRefined at the union wrapper like today): CHECK { type:'check', kind:'predict'|'classify', prompt, options?:[{label, correct, feedback}] (2-5, exactly one correct in predict), buckets?:[string] (2-3), items?:[{label, bucket:index, feedback?}], reveal?:string } — refine kind-conditional fields; feedback text is mandatory because confronting the named misconception IS the widget. SEQUENCE { type:'sequence', actors:[{id,label}] (2-6), steps:[{from,to,label,kind:'request'|'response'|'event'|'timer'|'note', status?:'ok'|'lost'|'late'|'error', state?:Record<string,string>, when?:toggleRef}] (2-30), toggles?:[{id,label,default:boolean}] (max 3), caption? } — refine from/to in actors, when references a declared toggle (allowing ! negation); the optional per-step state map lets the same widget render race interleavings (inventory-race, dual-write, GET-then-INCR) with a visible shared-variable row. TOPOLOGY { type:'topology', nodes:[{id,label,kind:'client'|'lb'|'service'|'db'|'cache'|'queue'|'cdn'|'zone'|'external', note?}] (2-16), edges:[{from,to,label?,kind:'sync'|'async'|'replication'}], stages?:[{adds:[nodeId], note}] (max 8, staged reveal with per-stage justification), layout:'lr'|'tb' } — deterministic layered layout computed at render (no physics, capped at 16 nodes so a Sugiyama-lite we own suffices); refine edge endpoints and stage ids exist. CAPACITY-CALC { type:'capacity-calc', inputs:[{id,label,min,max,step,default,scale:'linear'|'log',unit?} | {id,label,options:[{label,value}]} ] (1-6), outputs:[{id,label,expr,unit?,precision?,plot?:'sparkline'}] (1-6), narrative? } — expr is NOT executable code: a whitelisted arithmetic mini-grammar (identifiers, numbers, + - * / ^ ( ), ceil/floor/log10/pow) parsed by an ~80-line recursive-descent evaluator we own, validated at parse time (unknown identifier = schema error), preserving the specs-are-data-not-code rule; the select-input variant and sparkline output let this one engine absorb availability-calc, fanout-explorer/fanout-sim, tail-latency-explorer, retry-storm math, burn-rate, erasure-coding overhead, and utilization-curve. (3) Boundaries and bundle: everything stays client-side — no server routes, no Firestore writes (lessons are ungated; check answers are unpersisted local state, with an optional later analytics event). The 200+ lesson count is irrelevant to bundle size (content is per-route), but the widget component library is not: today CsDiagram is imported eagerly into the shared markdownComponents, so 25 new components would tax every /learn page including SQL/Python. Plan: keep zod parsing eager (small, gives instant validation + a correctly-sized placeholder to avoid CLS), but the cswidget dispatch component loads via next/dynamic/React.lazy with a Suspense fallback showing the caption; split sims into a second chunk from checks if the first chunk exceeds ~40KB gz. framer-motion and zod are already in the bundle — marginal cost is our own component code only. (4) A11y: WidgetFrame provides (a) native inputs only — <input type=range> with label + aria-valuetext including units, toggles as buttons with aria-pressed, checks as fieldset/legend radio groups — so keyboard support is free; (b) one polite aria-live region per widget announcing each state change as text (the current sequence step's label+note, the recomputed calc outputs, check feedback), making the text description the source of truth and the SVG presentational (aria-hidden) — the animation is an enhancement of a text log, never the only channel; (c) prefers-reduced-motion via the existing useReducedMotion pattern: transitions become instant state swaps and Play becomes step-only, sims remain fully functional since state changes are discrete renders; (d) status encoded by icon/pattern + word (lost = dashed + 'dropped'), never color alone; focus moves to feedback on check reveal. (5) External libraries: NONE. The only candidates are an expression evaluator (expr-eval is under-maintained; owning 80 lines is cheaper than auditing a dep), a layout engine (unneeded at <=16 nodes with authored stages), and d3-shape for curves (trivially hand-rolled paths). Mermaid and physics-graph remain rejected per the standing verdict. (6) Tests mirror content-integrity.test.ts: generalize the fence extractor, walk level0..11, parse every csdiagram AND cswidget fence against the schemas (invalid spec or swallowed prose fails CI), render each through the real Markdown pipeline under jsdom. ## Product / pitch

An interactive System Design path is a genuine differentiator versus DDIA/ByteByteGo, but only if the 66 proposed slugs are ruthlessly consolidated to roughly 15 built components (many slugs become JSON configs of a shared engine, not new code). The pitch-worthy claim is: "you do not read about consistent hashing, you break it, and every misconception you hold gets caught by a check and fed into spaced repetition." Ranked by demo-wow x learning-outcome x reach, the top 5 are: (1) check (211 lessons, the only widget that moves WCSR at curriculum scale, and its attempt data is the retrieval signal FSRS can later consume), (2) sequence with failure toggles (77 lessons, the workhorse for every temporal mechanism from TLS handshakes to saga compensation, and it absorbs inventory-race and retry-storm as configs), (3) capacity-calc as a generic formula-slider engine (the L0 estimation module IS this widget, and availability-calc plus tail-latency-explorer are just configs of it), (4) hash-ring (small reach, maximal wow: THE demo moment), (5) partition-sim (the CAP decision made tangible, anchors the hardest theory level). THE single demo moment is hash-ring in sd-l3-consistent-hashing: add a node under mod-N and watch most keys shatter and remap, flip to the ring and only ~1/N move, toggle virtual nodes to smooth load. It is fully client-side, legible in ten seconds to both a CS student at a demo table and a non-technical competition judge, and it upgrades a famous interview topic. The 60-second touchable slice is three deep-linked lessons on a demo playlist: sd-l0-fermi-estimation (capacity-calc sliders driving live QPS), sd-l0-clarify-scope (one predict-then-reveal check), sd-l3-consistent-hashing (hash-ring). All ungated, all client-side, hotspot-safe per the standing demo rules. Sequencing: check ships first because it moves WCSR for existing learners this month with near-zero component cost (one fence-driven quiz renderer, then authoring across the 152 high-value lessons, starting with misconception-rich L2/L5/L8); the pitch slice (hash-ring, capacity-calc, partition-sim) builds in parallel as three small isolated components; sequence is the biggest single build and ships third with iterative authoring; the sim vocabulary (cache-sim, queue-sim, rate-limiter, quorum-explorer, replication-lag) follows for L3/L4/L6. Scope warnings: the long tail of 35+ single-lesson widgets (order-book, concurrent-edit, ann-tuning, abr-sim, erasure-coding, trie-topk, chunk-dedup, and the L10/L11 tail generally) is gold-plating that would consume months for 1 lesson each; concurrent-edit and ann-tuning carry outright correctness risk (a toy OT/CRDT or a fake recall surface that misleads is worse than prose); topology must stay a constrained staged-reveal template or it becomes the physics-graph library re-entering through the back door, violating the standing engineering verdict. ### Recommendations

- [P0] **Ship the check widget first and author it into the worst 50 lessons**: One fence-driven predict-then-reveal quiz renderer (csdiagram-style JSON in a `cscheck` fence) unlocks 211 lessons, and the curriculum's own 'Interview nuance' callouts make authoring mechanical. Prioritize L2, L5, and L8, where misconception density is highest and prose walls are worst. This is the only item that plausibly moves WCSR for existing learners before the Aug 25 launch window, because it converts every passive read into a retrieval session. Record attempts through the existing tutorial progress sync so widget engagement becomes measurable WCSR evidence for the pitch traction slide.
- [P0] **Build the 60-second demo playlist: capacity-calc, check, hash-ring**: Three small isolated components in three deep-linked ungated lessons: sd-l0-fermi-estimation (DAU/peak sliders driving live QPS), sd-l0-clarify-scope (one check), and sd-l3-consistent-hashing (hash-ring with mod-N vs ring remap and virtual-nodes toggle). All pure client-side SVG + framer-motion, hotspot-safe, no network calls after page load, consistent with the standing hard demo rules. Add a /learn demo entry link so a booth visitor reaches the first widget in one tap.
- [P0] **Consolidate 66 slugs into ~15 components before any building starts**: Final build list: check, sequence (with failure-toggle and interleaving modes), topology (constrained staged-reveal), capacity-calc engine (absorbs availability-calc, tail-latency-explorer, and later burn-rate as configs), segmenting, queue-sim, partition-sim, cache-sim, quorum-explorer, replication-lag, rate-limiter, hash-ring, watermark-sim (absorbs watermark-window and stream-windows), lb-strategies, shuffle-shard-sim, fan-out (fanout-explorer + fanout-sim), geo-grid (absorbs geo-cells), circuit-breaker-sim (absorbs circuit-breaker), plus table and er as extensions of existing csdiagram types. - [P1] **Extend the csdiagram subsystem; do not build a parallel widget stack**: Reuse the proven extract.ts/schema.ts/CsDiagram.tsx pattern: fence-labeled JSON, zod validation, theme-aware, reduced-motion-aware, render-based content-integrity tests over every authored instance.
