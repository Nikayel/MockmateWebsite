You forget solved problems because you never practiced retrieving them. Solving something once and then "reviewing" it by rereading your old solution builds recognition: the code looks correct when it is in front of you. An interview never puts it in front of you. It asks you to produce a solution from an empty editor, and producing is a separate ability that only strengthens when you actually produce. The gap between "I recognize this" and "I can write this" is what feels like forgetting.

The rest of this post covers why that gap opens, how a memorized solution differs from a retained pattern, a worked example that turns one problem into something reusable, and a review system you can run in a text file.

## Why you forget LeetCode problems you already solved

Memory researchers separate how well something is stored from how easily you can pull it back out. Hermann Ebbinghaus measured the second half in 1885, learning lists of nonsense syllables and testing himself at increasing delays. His result, the forgetting curve, is that recall drops steeply soon after learning and then flattens out. Jaap Murre and Joeri Dros replicated the original experiment in 2015 and found the same curve shape. Ebbinghaus also found the fix in the same work: relearning the material at intervals flattened the decline.

None of that is specific to programming, and syllables are not algorithms. What carries over is the shape of the problem. A solution you produced once and never produced again is sitting on that curve.

Four habits push a solved problem down it faster.

| Cause | What it looks like | Why it costs you |
|-------|--------------------|------------------|
| Passive review | Rereading your old solution or the editorial | Reading builds recognition. The interview tests production. |
| No retrieval attempt | Opening the answer before you have struggled | The effortful attempt is the part that strengthens recall |
| Weak pattern labeling | Filed as "Two Sum" rather than "complement lookup with a hash map" | An unlabeled solution can only be recalled by its problem, so nothing transfers |
| Long gaps | First review is a month later | You are relearning from scratch instead of refreshing |

The last two are the ones people underrate. Weak labeling is why solving 300 problems can still leave you stuck on the 301st: you built 300 separate memories instead of a small set of reusable ones.

## Memorizing a solution is not the same as retaining a pattern

A memorized solution is keyed to the problem that produced it. You can recall it when you see that problem again, and only then. It is a lookup table with one entry.

A retained pattern is keyed to a situation. It says: when the input looks like this and the brute force costs that, reach for this move. That key fires on problems you have never seen, which is the only case an interview cares about, because the interviewer picked a question specifically hoping you have not seen it.

The practical difference shows up in what you can say out loud. If your recall is a memorized solution, you can describe the code. If it is a pattern, you can say why the code is shaped that way and what you would change if the constraints moved. Interviewers ask the second question constantly, and it is not a trick. It is a direct test of which of the two you have.

## A worked example: turning Two Sum into a pattern you can reuse

Take the standard version: given an array `nums` and an integer `target`, return the indices of the two numbers that add up to `target`.

The memorized version is "use a hash map." That sentence recalls nothing on a problem that does not say Two Sum on it. Here is the same knowledge written as a pattern card instead.

**Complement lookup with a hash map**

- **Trigger.** You need a pair, or a completion, and the brute force is a nested scan at O(n²).
- **Move.** Walk the input once. At each element, compute what would complete the answer, look that up in a structure holding everything seen so far, then record the current element in that structure.
- **Cost.** O(n) time, O(n) space. You are buying time with memory.
- **Failure modes.** Look up the complement before you insert the current element, or a number pairs with itself. Duplicate values need a decision about which index wins. The array is not sorted, so nothing about the output order is free.

Notice the card never says "Two Sum." That is what makes it reusable. Three problems that are not Two Sum:

- **Contains Duplicate.** The completion is "this same value again," and the structure holding what you have seen is a set instead of a map, because you do not need an index. Same walk, same lookup, less bookkeeping.
- **Longest Substring Without Repeating Characters.** What you have seen maps each character to the last index where it appeared, which lets the window jump forward instead of crawling. Same idea, different bookkeeping.
- **Subarray Sum Equals K.** Keep a running prefix sum and store the prefix sums seen so far in a hash map. At each index, look up `prefix - k`. That is Two Sum with prefix sums substituted for values, and it is a hard problem the moment you file Two Sum as a fact about pairs rather than as a fact about completions.

That last one is the whole argument in miniature. The transfer costs nothing if you stored the pattern, and it is a fresh problem if you stored the solution.

Both halves of the move are ordinary language features before they are interview tricks, so a shaky half is worth fixing directly rather than through more problems. The [Python dictionaries lesson](/learn/python/fundamentals/py-l1-dicts) covers reading and assigning safely, and [choosing the right data structure](/learn/python/fundamentals/py-l1-complexity-choice) covers when a set or dict replaces a scan of a list, which is the decision this pattern actually turns on. [Recursion](/learn/python/fundamentals/py-l1-recursion) decays faster than most patterns because you use it less often between interviews, so it is usually the first thing worth rerunning.

Write your own cards. A card someone else wrote is something you read, which puts you back in the passive half of this article. For a starting list of which patterns are worth carding at all, the [15 DSA patterns](/blog/15-dsa-patterns) post covers the ones that recur most.

## A review system you can run in a text file

You do not need software for this. You need five rules and somewhere to write three columns.

**1. Attempt before you look.** Blank editor, no notes, no old solution. Give it the time you would get in a real round. If you cannot start after a couple of minutes, read your own pattern card, not the solution. The card is a hint. The solution is the answer, and reading it ends the review.

**2. Review the pattern, not the problem.** Reuse the same problem too often and you start recalling the specific code again. Rotate through different problems that share a card, which is why the card lists more than one.

**3. Space the reviews and let the gap expand.** A workable starting ladder is one day, three days, a week, two weeks, a month. There is nothing magic about those numbers. What matters is the direction: the interval grows after you produce the solution cleanly and shrinks back after you fail to.

**4. Interleave.** Mix patterns inside a session instead of doing eight sliding window problems in a row. Blocked practice feels better while you are doing it, because the pattern is already loaded and you never have to choose. Choosing is the skill.

**5. Log honestly.** Three fields is enough: date, pattern, outcome.

```
2026-03-04  complement lookup   produced         next: 03-11
2026-03-04  monotonic stack     needed a hint    next: 03-05
2026-03-05  sliding window      could not start  next: 03-06
```

"Needed a hint" and "could not start" are the useful rows. If you only ever write "produced," your ladder is too short or you are looking things up before you struggle.

One scheduling note that decides whether this survives: do the due reviews before any new problem, not after. New problems are the enjoyable part and they will eat the whole session otherwise. Twenty minutes of review in front of an hour of new work is a sustainable shape. An hour of new work followed by whatever time is left is not.

## What the research actually supports

The three findings this system rests on are real, and it is worth knowing what they do and do not claim.

- **Retrieval beats rereading.** Henry Roediger and Jeffrey Karpicke (2006, *Psychological Science*) had students either take practice tests on a passage or restudy it for the same amount of time. The tested group retained more on a delayed test. The restudy group predicted the opposite, which is the uncomfortable part: rereading feels more effective than it is.
- **Spacing beats cramming.** Nicholas Cepeda, Harold Pashler, Edward Vul, John Wixted and Doug Rohrer (2006, *Psychological Bulletin*) reviewed a large body of verbal recall studies and found distributed practice outperformed massed practice at the same total study time.
- **Interleaving beats blocking for transfer.** Doug Rohrer and Kelli Taylor (2007) found students who practiced mixed problem types did worse during practice and better on a delayed test than students who practiced one type at a time.

The honest caveat: none of these studies used code. They used word lists, prose passages and math problems. What transfers to interview prep is the direction of each effect, not a specific number of days. Treat the interval ladder above as a convention that works, not as a research result, and be suspicious of anyone quoting you an exact retention percentage for algorithms.
