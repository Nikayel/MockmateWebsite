01

How to read this

Each finding is collapsed by default. Open one to see the same problem explained from three jobs you're growing into. The goal isn't to memorize 18 bugs — it's to internalize the handful of mental models underneath them.

Lens · PM

Is this a launch blocker?

Severity ≈ how easy to exploit × how much it touches. A trivially-exploitable flaw that hits every user's data outranks a clever one that hits nobody. PMs turn risk into a go / no-go.

Lens · Engineer

Where's the flaw, what's the fix?

The exact line, the exact change, and the reusable pattern — so the next route is written correctly the first time instead of re-audited later.

Lens · Data engineer

Who can touch which data?

Every write crosses a trust boundary. The question is always: does this mutation carry a “…where owner = caller” clause the server actually enforces?

02

Six mental models

These recur across the whole audit. Once you can name them, most of the findings collapse into “oh — that one again.”

Concept

Trust boundary

The line between code you control (server) and input you don't (the browser, the request body). Anything crossing it is a lie until verified. The client is a suggestion; the server is the truth.

Concept

IDOR

Insecure Direct Object Reference: acting on an ID from the request without checking the caller owns that object. “Update session X” must become “update session X if it belongs to me.”

Concept

Client-attested vs. server-authoritative

If the browser reports “I passed / I used 0 sessions” and the server believes it, the browser is now in charge of your billing and your grades. Trust the server's own count.

Concept

Defense in depth

Rules and server checks and conservative reads. When one layer is awkward to fix safely, a second layer can still close the hole today without breaking the flow.

Concept

Cold-start UX

The first run is always the slowest (downloads, warmups). If your timeout can't tell “still loading” from “stuck,” you punish exactly the users you're trying to onboard.

Concept

Fail closed, and fail readable

When a secret is missing or a token is bad, deny by default — never accidentally allow. And when you deny, say what happened in words a human can act on.

critical high medium shipped
FEEDBACK-IDORCriticalShipped
Anyone could overwrite any user's interview scores
›
app/api/feedback/persist/route.ts+ instant · status · process · stream

The feedback routes had no authentication at all. They read userId and sessionId from the request body and wrote scores, feedback, and mastery straight into interview_sessions — for whatever session ID you sent.

Product

Ship-blocker. Exploit cost is near-zero (no login needed) and blast radius is total (every user's results and spaced-repetition schedule). If a stranger can rewrite your grades, the product's core promise — an honest read on your readiness — is gone. This is exactly why “require sign-in on data/cost routes” is a launch gate.

Engineer

The route trusted body identity and did a blind adminDb…doc(sessionId).update(). Fix: verify the Firebase token with verifyAuth, reject if body.userId ≠ token uid, then load the session and confirm user_id === caller before writing. The Edge stream route needed a new REST verifier (lib/auth-edge.ts) since it can't load the Admin SDK.

Data engineer

Textbook IDOR. The write crossed the trust boundary with no ownership predicate. In data terms every mutation needs a WHERE owner = caller — enforced server-side, because Firestore rules don't run on Admin-SDK writes. The doc shape is a contract; the server is the only place it holds.

The fix, in one line

Never derive identity from the body. Verify the token → match the claimed user → confirm the target doc is owned by that user → then write.

The transferable lesson

Two questions for every mutating route: “who is calling?” (authentication) and “are they allowed to touch this specific object?” (authorization). The second is the one that's quietly skipped.

FEEDBACK-COSTHighShipped
Unauthenticated callers could burn your AI budget
›
feedback/process · stream · instant

The same routes also kick off paid LLM work. process with processAll:true would churn through everyone's pending jobs; stream streamed model output to anyone.

Product

This is a money leak, not just a data leak. Unauthenticated cost paths turn your launch into someone else's free compute. The mitigation to internalize: gate anything that spends money behind identity and a rate limit.

Engineer

process is dual-use, so it now accepts either a CRON_SECRET (for batch mode, timing-safe compared, failing closed if unset) or a user token that may only process its own job. The client hooks were updated to attach getCurrentUserToken() on every call — otherwise the real flow would 401.

Data engineer

Batch operations are a privilege. “Process all pending jobs” is an admin/cron capability; a signed-in user gets exactly one verb — “process the job I own.” Scope the blast radius of every bulk endpoint.

The fix, in one line

Split the identities: cron secret unlocks batch; a user token unlocks only their own record. Attach the token in the client, or you break your own flow.

The transferable lesson

When you add auth to a route, you must update its callers in the same change — a “secure” endpoint whose UI can't reach it is just an outage.

PYODIDE-COLDSTARTHighShipped
Slow-network learners could never finish their first Python run
›
lib/workspace-execution/python-sandbox/worker-runner.tspublic/workers/python-sandbox-worker.js

The 5-second “Run” timeout included the multi-megabyte Pyodide download. On a slow connection the first run timed out, showed a misleading “check for infinite loops” error, and killed the worker — discarding the download, so every retry restarted from zero.

Product

This punishes your most important moment — a new learner's very first run — and blames them (“infinite loop”) for your cold start. Silent first-run failure is an invisible churn machine: they don't file a bug, they just leave. For a Python curriculum, this is a launch blocker even though nothing is “insecure.”

Engineer

One timer was doing two jobs. Now there's a 60s boot timeout that swaps to a 5s execution timeout the moment the worker signals exec-start — so cold starts get patience and runaway loops still get caught fast. A failed load no longer caches forever, so a brief offline blip can recover without a page reload.

Data engineer

Instrument the boundary you care about. Measuring boot + execution as one number hides which half is slow. Separate the phases and your telemetry can finally answer “are people bouncing off cold start?”

The fix, in one line

Give “still loading” and “stuck in a loop” different clocks and different messages — a slow download is not an error.

The transferable lesson

Timeouts encode a hypothesis about what “too long” means. If one timeout spans two very different phases, it will misdiagnose one of them — and error copy that guesses wrong erodes trust.

PYODIDE-FORGED-PASSHighShipped
A previous run's answer could make the wrong code “pass”
›
public/workers/python-sandbox-worker.js

Every run executed in the same Python global namespace. The test harness finds the candidate function via globals() — so if your current code didn't define it but an earlier run did, the stale function satisfied the test and the lesson was marked complete.

Product

A learning tool that says “correct!” for code that isn't teaches the wrong thing — the single worst outcome for an education product. Correctness of the grader is the product. Quietly, this also inflates your “completion” metrics.

Engineer

State leaked between runs. Each execution now gets a fresh namespace (pyodide.toPy({})), and PyProxies/temp files are destroyed after use. Because the DSA harness bundles the user's code and the tests into one self-contained string, running it in a clean namespace is both safe and correct.

Data engineer

Idempotency & isolation. A test run must be a pure function of this submission, not of session history. Shared mutable state is the enemy of reproducible results — the same defect that makes flaky test suites.

The fix, in one line

Reset the world between runs — no definition should survive from one execution to the next.

The transferable lesson

“Passes the test” is only trustworthy if each run starts from a known-clean state. Reused interpreters, warm caches, and singletons all leak state that turns green into a lie.

QUOTA-RESETHighShipped (depth)
A user could reset their own session limit
›
lib/quota-enforcement.tsfirestore.rules · profile_quota

Firestore rules let a user create their own profile_quota doc with sessions_used: 0. The server read the first matching doc — so minting a fresh zero-usage doc reset the free-tier limit.

Product

This is the free-tier fence with a gate left open — directly erodes the reason to upgrade. Note the bound, though: a server-only budget cap still limits real spend, so it's “free sessions,” not “infinite money.” That nuance is why it's High, not Critical — severity is about actual blast radius, not worst-imaginable.

Engineer

The full fix (server-only quota writes) is coupled to an existing anniversary-vs-calendar period mismatch and the billing flow — risky to ship without a Firestore emulator. So the safe layer went in now: the server reads the most-conservative matching doc (highest sessions_used). A forged zero-usage doc can no longer lower the count. The complete follow-up is written up in PRE-LAUNCH-FIXES.md → QUOTA-1.

Data engineer

When duplicate records can exist, your read has to define which one is authoritative. “First by date” trusted an attacker-controllable field; “max usage” is monotonic and can't be gamed downward. Choosing the aggregation is a data-integrity decision.

The fix, in one line

Two layers: read defensively today (take the highest usage), and make writes server-authoritative next (with emulator tests) — don't ship a risky rules change blind.

The transferable lesson

When the correct fix is risky to verify, a conservative read-side layer can close the hole now without breaking the flow. Defense in depth buys you safe time.

NOTIF-INJECTIONMediumShipped
A user could plant a notification in someone else's inbox
›
firestore.rules · in_app_notifications

The update rule checked you owned the notification now, but didn't stop you from reassigning its owner. You could rewrite a notification's text into a phishing message and set its userId to a victim.

Product

Phishing that renders inside your own trusted UI is worse than external spam — users have their guard down. Reputational risk out of proportion to the “medium” label.

Engineer

The sibling notifications rule already pinned the owner on write; in_app_notifications didn't. Fix: pin request.resource.data.userId == auth.uid and restrict writable keys to the read/dismiss state via affectedKeys().hasOnly([…]).

Data engineer

“Mark as read” should mutate state, never ownership or content. Column-level write permissions matter: allow the two fields the action needs, deny the rest.

The fix, in one line

On update, freeze the owner and the content — only the read/dismissed flags may change.

The transferable lesson

“Can edit” is not one permission. Scope which fields an action may touch; an unrestricted update is a re-write.

API-HARDENINGMediumShipped ×4
Four smaller holes: DoS, privilege check, identity override, billing link
›
transpilerate-limit-feedbacknotificationscustomer-portal

A cluster of medium issues fixed together — each a clean example of a distinct class of bug.

Product

None alone blocks launch, but together they're the “unlocked windows” of the app. Cheap to close now, expensive to explain after an incident. Batch the low-risk hardening before you go live.

Engineer

transpile: unbounded CPU → added rate limit + 100KB cap. rate-limit-feedback: admin gate read the user-writable profiles.is_admin → switched to RBAC verifyAdminAccess. notifications: { userId, ...body.context } let the body override identity → spread body first. customer-portal: refused to link a Stripe customer owned by a different user.

Data engineer

The privilege-check one is the keeper: never authorize on a field the subject can write. If a user can set their own is_admin, it isn't an access control — it's a suggestion box. Authority must come from a source the subject can't edit.

The fix, in one line

Cap untrusted work, authorize from an unwriteable source, spread trusted values last, and confirm ownership before linking money.

The transferable lesson

Object-spread order is a security boundary: { ...untrusted, trusted } is safe; { trusted, ...untrusted } hands the keys to the caller.

QUOTA-1HighNeeds staging
Make session quota server-authoritative
›

The read-side defense is live, but profile_quota is still client-writable and the client (anniversary billing) and server (calendar month) disagree on where a period starts.

Product

Trustworthy usage accounting is the backbone of monetization. Worth doing right — behind the emulator — rather than fast.

Engineer

Move quota writes to an authenticated Admin-SDK route, set the rule to write: if false, and unify on one period model with a deterministic doc id {uid}_{period}. Verify the free/pro/rollover flow in the Firestore emulator before shipping.

Data engineer

One writer, one period key, one doc per period. Deterministic ids turn “which record is real?” into a non-question.

Why it's not shipped yet

The safe fix needs an emulator to prove it doesn't break paid sessions. “Don't ship a security fix you can't verify” is itself the lesson — a broken checkout is also a flaw.

API-IDOR-1MediumOpen
session/metrics trusts a session id it never checks you own
›
app/api/session/metrics/route.ts

The token is verified, but every action operates on body.sessionId with no ownership check — the same IDOR class as the feedback routes, one layer down.

Product

Lower blast radius (mostly in-memory metrics), so medium — but it's the identical pattern, and patterns spread. Fix it so the codebase's “shape” stays correct.

Engineer

Stamp the owner onto the metrics record at session_start; reject later events whose record owner ≠ caller. Reuse the ownership check from feedback/persist.

Data engineer

Ownership isn't checked once at the door — it's checked on every operation against the object, because ids are guessable.

AUTH-GATE-1MediumOpen
The “hard gate” on the Python tutorial is a paper gate
›
proxy.ts

The route guard treats any value in an auth cookie as “logged in” — document.cookie = "firebase-auth-token=x" walks right past it into the signed-in-only tutorial.

Product

The danger is the false confidence: a comment says “hard gate,” so the next engineer builds on it as if it's real. Mislabeled security is worse than none.

Engineer

Either verify the session cookie in the proxy, or (simpler) demote the comment to “cosmetic” and make sure gated content is fetched from an authenticated API — which the progress endpoints already require.

Data engineer

Presence ≠ validity. A cookie existing tells you nothing; only verifying its signature does. Never let an unverified token stand in for an identity.

The transferable lesson

A gate is only as strong as what it checks. “There is a cookie” is not authentication; “this cookie is a valid, unexpired, signed token” is.

DATA-TELEMETRYLowShipped
Your server-side analytics were silently going nowhere
›
lib/analytics-server.ts

The server telemetry helper used the client Firestore SDK, which has no auth context on the server — so Firestore rules denied every write and the catch swallowed it. Months of “tracked” events, gone.

Product

The scariest bugs are the silent ones. You'd make launch decisions on dashboards that were quietly empty. Always confirm your instrumentation actually lands before you trust it.

Engineer

Wrong SDK for the runtime. Server code writes with the Admin SDK (bypasses rules, carries service credentials). Switched the helper to adminDb; a swallowing catch hid the failure for a long time.

Data engineer

This is your job's cautionary tale: a pipeline that fails silently is worse than one that fails loudly. Verify writes land end-to-end, and never let a catch turn a broken pipeline into a green one.

The fix, in one line

Use the runtime's correct SDK, and don't let error-swallowing hide a dead pipeline.

The transferable lesson

“No errors” is not “it works.” A try/catch that logs and moves on can mask a total outage of a background system for months. Assert the effect, not the absence of a throw.
